기존 개발에서 확인하고 수정한 경로는 빈/부분 프로필 응답을 삭제로 취급하는 처리, 늦은 응답의 덮어쓰기, 과거 reset 신호, 실행 중 저장소 예외, 기기 비밀값의 불필요한 재생성입니다. 해당 수정은 재제작하지 않고 보존했습니다. 실제 앱에서 부분200·503·새로고침·가상 백그라운드 복귀 후 같은 프로필 ID/PIN과 하트·채팅 기록을 확인했습니다. 이번 누적 DB 검사에서는 실제 API 서버를 재시작하고 150명의 닉네임/PIN·입금승인·카드 복원을 확인했습니다. 정상17시 초기화와 인증/소유권 검사는 유지합니다.

## 6. 아직 필요한 기술·운영 작업

1. 150명 동시 구간의2초 목표 개선, 더 긴 지속/실시간 화면 반영·메모리 추이 검사. 인증·DB 잠금/재고 검사는 유지합니다.
2. 131개 기준 중 PARTIAL/UNKNOWN인 모든 메뉴·모바일 키보드·확대/회전·접근성 조합과 실제 Galaxy/iPhone 잠금/은행/카카오톡 복귀·푸시 확인.
3. 승인 취소의 입장/추첨/장소 권한 회수는 검사했지만 기존 현장 하트·채팅 세션을 즉시 중지하는 범위는 별도 검토·보완 필요. 기록을 삭제하거나 자동 환불하지 않습니다.
4. 현재 운영 DB·업로드·일치 키의 보호 백업/격리 복원. 이후 기존 서비스에 호환 배포하고 실제 배포ID·실행 SHA·신규 신청 차단 확인.

운영자가 결정할 정책은 한 묶음으로 정리합니다. 신청30일/문의90일/재사용1년/백업30일 등은 **검토안**이며 자동 확정하지 않습니다. 각 기록의 보관 목적·만료일 기준·정산 분쟁 예외·백업 만료와 삭제 요청 처리 담당을 확정해야 합니다. 정산180일을 법정기간으로 주장하지 않습니다. 기술적 검토/삭제 요청 경로는 유지하며 운영 자동 삭제는 비활성입니다. 기존 행사시간·선입금/수동1/N 정산은 다시 묻지 않습니다.

## 7. Supabase 연결과 기존 사이트에서 확인하는 순서

현재 필요한 연결은 `SUPABASE_ACCESS_TOKEN`입니다. 토큰 화면에서 BINPC2만 선택하고 **Backups Read, Database Read, 나머지 None**으로 만듭니다. Codex 시크릿 관리의 해당 이름 **가운데 값 칸**에 넣고 저장·환경 적용합니다. 대상은 `api.supabase.com`. 채팅/GitHub에 토큰을 붙이지 않습니다. 읽기 권한은 백업/스키마 확인용이며 완전한 덤프·격리 복원 완료를 자동 보장하지 않습니다.

Netlify/Render 인증은 이미 HTTP200으로 확인됐습니다. 과거 proxy403을 현재 실패로 반복 보고하지 않습니다. 기존 배포 승인도 유지되며, 이번 미배포 사유는 운영 DB/업로드 백업·격리 복원 미완료입니다. 새 사이트·유료 서비스·main 병합·키 교체는 하지 않았습니다.

배포 조건을 충족한 뒤 기존 **https://binpc2.netlify.app**에서 관리자 로그인 → **술번개 → 행사 설정·기록·관리 도구 → 선착순 시험실**로 들어갑니다. 금/토/투어와 가상3등을 선택하고 승인→프로필→입장→카드→재열기를 시험합니다. 초기화는 시험실 범위만 사용합니다. 현재 주소에 V12가 반영됐다고 안내하는 것이 아닙니다.

내부 검사를 마친 앱은 [테스트ON·일반신청닫힘](v12-validation-20261029/final-local-admission-state.json)으로 되돌려 두었습니다. 이는 운영 사이트 상태 확인과 다릅니다.

휴대폰에서는 같은 시험 참가자를 만든 뒤 고유번호 확인 → 잠금/해제 → 은행/카카오톡 왕복 → 새로고침 → 인터넷 끊기/복귀 순서로 같은 프로필·신청·입금·하트·채팅이 남는지 확인합니다. 실제 신규 신청/송금은 하지 않습니다. 테스트 OFF만으로 접수는 열리지 않으며, 사용자의 별도 오픈 확인 전 `publicAdmissionOpen=false`를 유지합니다.
