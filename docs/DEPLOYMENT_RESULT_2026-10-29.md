4. 이미 확인한 기존 서비스 ID·배포 ID·코드를 재개 기준으로 사용한다. 기존 `SESSION_SECRET`의 암호화 보존은 완료했지만 운영 DB/업로드 전체 백업과 격리 복원은 별도로 완료해야 한다. 원본 개인정보나 비밀값을 공개 파일로 내보내지 않는다.
5. 필요한 기존 스키마 적용을 안전하게 확인하고 같은 소스의 API와 화면을 기존 Netlify·Render에 호환되게 배포한다. 새 서비스·새 사이트·공개 터널, main을 통한 자동 배포 우회는 사용하지 않는다.
6. 배포 목표는 **테스트 ON + 일반 신청 차단(`publicAdmissionOpen: false`)**이다. 실제 deploy ID, 실행 소스·코드 지문, 양쪽 호환과 신청 차단을 확인한 뒤 사용자에게 테스트 방법을 안내한다. 테스트 OFF/실제 모집 오픈 명령은 대신 실행하지 않는다.
7. 사용자가 테스트를 마치고 별도로 실제 오픈을 확인하기 전에는 웹·오픈채팅 모집을 시작하지 않는다. 운영 개인정보 정책·사진·외부 발송·자동 삭제·금전 이동의 별도 조건도 유지한다.

현재 남은 외부 연결은 **기존 Supabase의 관리 인증 하나**다. [Supabase 관리 토큰](https://supabase.com/dashboard/account/tokens)을 환경 시크릿 관리의 `SUPABASE_ACCESS_TOKEN` 값 칸에 연결하고 대상은 `api.supabase.com`으로 제한한다. 초안을 저장·게시해도 현재 실행의 실제 인증 성공은 따로 확인한다. 토큰을 채팅이나 GitHub에 넣지 않는다. 기존 Netlify/Render 키 재입력·새 사이트·새 유료 DB·배포 재승인은 필요하지 않다.
