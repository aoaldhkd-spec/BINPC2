# 기존 BINPC2 반영 준비 — 실행 전 검토본

별도 시험사이트는 만들지 않는다. 이 문서는 반영 순서이며 **main 병합·운영 배포·서비스 설정 변경·실제 모집·발송·운영 데이터 파기를 실행한 기록이 아니다.** 최신 코드/검사 범위는 [최종 보고서](EVENT_HUB_V6_COMPLETION_2026-10-27.md), 기능별 상태는 [통합표](EVENT_HUB_V6_INTEGRATED_CHECKLIST_2026-10-27.md)를 따른다.

## 1. 확정할 코드와 보존 자료

- `feat/event-hub-v6-20261027`의 최종 소스 SHA와 코드 지문을 보고서/CI에서 확인한다. frontend와 API는 같은 소스로 빌드한다. 운영 점검 화면의 frontend/API 지문 불일치 경고를 무시하지 않는다.
- 기존 main, 원격 개발 브랜치, 로고 원본8종·추적표·체크섬, 실패 기록, 기존 전체 bundle을 보존한다. Git bundle은 소스 복구본이며 DB·업로드·비공개 키 백업이 아니다.
- 운영 `SESSION_SECRET`은 이벤트 원장 암호화 키의 입력이다. 기존 값을 바꾸거나 개발/시험 키로 덮어쓰지 않는다. DB 백업과 해당 비밀값을 서로 다른 비공개 보관소에 보존하고 복원 권한자를 정한다. 공개 GitHub/보고서/ZIP에는 넣지 않는다.
- 현재 운영의 실제 배포 SHA·DB 스키마·키·백업 복구는 이 세션에서 확인하지 않았다. 배포 담당자가 별도 승인 후 확인할 항목이다. 운영 DB에 시험 신청자나 부하를 넣지 않는다.

## 2. DB 준비 필요 여부와 순서

**V6 원장이 아직 없다면 새 테이블이 필요하며, 기존 V6 원장이 있다면 추가 인덱스가 필요하다.** `artifacts/api-server/migrations/20261027_event_hub.sql`은 `IF NOT EXISTS`로 원장/RLS/인덱스를 더한다. 삭제·TRUNCATE·기존 업무 payload 변경은 없다. 작은 변경이어도 인덱스 생성 중 잠금 영향이 있으므로 저사용 시간과 백업을 확인한다.

1. 현재 DB·업로드 원본·키·기존 배포 SHA를 비공개 백업한다. 별도 격리 복원본에서 기존 본인/입금/당첨 기록이 복원되는지 확인한다. 이번 검사 결과를 운영 백업 복원 완료로 바꾸지 않는다.
2. 기존 일반 BINPC2 기능/17시 운영은 유지하고, V6 신규 모집·자동방·혜택·경품·사진·테마는 OFF로 준비한다. 전체 이벤트 모듈을 꺼도 기존 기록 조회와 관리자 후속 처리는 남는다. 일반 앱의 `session_active`나 하트/채팅을 일괄 OFF하지 않는다.
3. 별도 DB 변경 승인을 받은 후 위 추가 스키마를 적용한다. 먼저 기존 데이터/키로 읽기 가능한지 확인한다.
4. 누적 원장이 많다면 선택적으로 HMAC 조회 메타데이터를 준비한다. 기본 CLI 실행은 **접속도 변경도 하지 않는 계획 출력**이다. 명시적 `--scope production --dry-run`은 읽기 전용 건수 확인이다. `--apply`는 production 모드, 기존 키, `EVENT_HUB_LOOKUP_MIGRATION_APPROVED=metadata-only-after-backup`, 실제 DB명과 일치하는 `EVENT_HUB_LOOKUP_DB_NAME`을 모두 요구한다. **이번 세션에서는 production에 실행하지 않았다.**
5. 이 준비 작업은 batch당 최대200건의 바깥쪽 HMAC/owner 조회 메타데이터만 더한다. 암호문·키·payload revision·업무 시간·DB updated_at은 바꾸지 않는 것을 실제 PG에서 검증했다. 이전 평문/메타데이터 없는 행도 호환 조회한다. 중간 중단 시 기존 원장은 남고 재실행 가능하다. 기록 삭제나 키 교체로 대신하지 않는다.

별도 CLI는 `artifacts/api-server/dist/event-hub-lookup-cli.mjs`이며 HTTP 관리자 버튼에 연결하지 않았다. 운영 화면에서 시간 변경·대량부하·DB 초기화·lookup migration을 실행할 수 없다.

## 3. 기존 주소에 기능 OFF로 반영하는 순서

1. 별도 승인을 받은 코드만 기존 배포 경로로 반영한다. 이번에는 Render/Netlify 설정을 변경하지 않았다. 사용자 확인 Netlify Stopped builds·Render main 추적을 유지했으며 관리 API로 독립 조회하지 못한 사실도 남긴다.
2. API와 React를 같은 코드 지문으로 올리고 기존 로그인·고유번호·하트·채팅·관리자·일별 초기화 회귀를 먼저 확인한다. 백엔드 오류 시 사용자 저장소를 지우는 방법으로 대응하지 않는다.
3. 관리자 → 술번개 → 운영 점검에서 실행 SHA/지문, 실제 검사 이력·환경·시각·실패를 확인한다. 현재 지문에 없는 결과는 과거 검사로 표시된다. 새로고침 클릭은 PASS를 만들지 않는다.
4. 실제 행사·은행·금액·장소·모집시간·권한을 운영자가 대조한 뒤 필요한 모듈만 개별 ON한다. 단순 전체 ON은 하지 않는다. 기존 승인자의 금액/장소/신청은 다시 쓰지 않는다.
5. 목적별 정책을 확정·저장·승인한 것만으로 production 접수를 열지 않는다. 별도 모집 승인 후에만 `EVENT_HUB_PRODUCTION_RELEASE=approved-v6`와 승인 정책의 정확한 `EVENT_HUB_RELEASE_POLICY_SHA256`를 적용한다. 정책을 수정하면 초안으로 돌아가며 지문이 달라져 신규 접수는 다시 차단된다.
6. 사진은 별도 동의/기간을 정하고 `EVENT_HUB_PHOTO_RELEASE=approved-photo`를 추가 승인할 때만 허용한다. 사진 기본 OFF, 자동 정산·송금·환불·외부 알림·자동 파기도 OFF로 유지한다.

## 4. 보스가 기존 주소에서 할 최종 휴대폰 검사

운영 반영 승인이 난 뒤 평소 BINPC2 주소에서 검사한다. 지금 새 외부 테스트 주소를 제공하는 계획은 아니다. 기능 시나리오는 관리자 **독립 시험실의 합성 데이터**로 확인한다. 운영 DB에 가짜 신청·가짜 입금·가짜 당첨을 넣지 않는다. 실제 행사/기존 계정의 변경은 운영자가 의도한 정상 사용 범위만 허용한다.

1. Galaxy Chrome/Samsung Internet와 iPhone Safari/PWA 각각에서 정상 본인 프로필·닉네임·고유번호, 하트 수/기존 대화, 현재 참가·신청·입금 상태를 먼저 기록한다. 계정/번호/비밀값을 공개 캡처하지 않는다.
2. 잠금30초→해제, 은행 앱→복귀, 카카오톡→복귀, 새로고침, 탭 닫기→같은 브라우저로 다시 열기를 차례로 수행한다. 매번 동일 프로필·고유번호·하트·대화·승인을 확인한다.
3. 비행기 모드에서 로딩/저장 실패가 나도 입력/기존 프로필이 남는지 확인하고 연결을 복원한다. 실패 중 미가입 화면이나 재입금 요구가 나오면 모집을 중지하고 시각·단계·배포 SHA를 비공개 기록한다. 저장소/인증을 지워서 증상을 숨기지 않는다.
4. 별도 격리 시험실에서 가상3/4등, 접수 시작 직전/정각, 늦참/종료 이후, 입금신고/관리자승인, 프로필 일부/완료,17시 전후와 카드/지급을 선택한다. 시험실은 운영 시계·재고·신청을 바꾸지 않는다. 시험실 PASS를 실제 DB/실기기 성적으로 바꾸지 않는다.
5. 진짜17시 이후 종료된 현장 프로필은 다시 복원되면 안 된다. 별도 신청·입금·당첨·지급 이력은 남아야 한다. 이 검사는 실제 시각/운영 절차로 관찰하고 운영 DB의 시계를 바꾸거나 수동 초기화를 실행하지 않는다.
6. 알림은 실제 발송 승인을 별도로 받은 후 지원 기기별로 검사한다. 내부 Chromium 결과로 OS 잠금·앱 회수·PWA 푸시 완료를 주장하지 않는다.

## 5. 중지·되돌리기

- 이상이 있으면 해당 행사의 신규 접수와 관련 모듈만 OFF한다. 기존 신청·입금·문의·당첨·지급 기록과 관리자 후속 처리는 보존한다.
- 문제 코드에 대한 롤백은 이전에 검증된 호환 소스로 한다. 추가된 테이블/인덱스를 삭제하거나 운영 데이터를 이전 백업으로 무조건 덮지 않는다. 배포 후 새 입금/신청이 있다면 DB 복원은 대조·복구 계획과 별도 승인이 필요하다.
- 동일 `SESSION_SECRET`, 업로드 원본, 기존 세션/기기 비밀값을 보존한다. `localStorage.clear()`, 키 재생성, 강제17시 초기화는 롤백 방법이 아니다.
- 다시 켜기 전에 오류/접수/입금/지급 장부를 대조하고, 해당 코드의 CI·관리자/참가자 권한·필수 프로필·중복 요청 검사를 확인한다.

다음 수치는 **검토용 권장안**이며 저장·확정·적용하지 않았다. 법정 보관기간이라고 주장하지 않는다. 분쟁/법률상 의무가 있으면 해당 기록만 사유·기간·접근자를 정해 보류하고 전체 개인정보를 무기한 보존하지 않는다.
