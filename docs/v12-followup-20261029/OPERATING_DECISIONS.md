# 운영자가 정할 것과 기존 사이트 반영 순서

배포 승인은 유지된다. 토큰은 연결됐다. 지금의 미배포 이유는 인증 재입력이나 새 시험사이트 승인이 아니다.

## 백업: 현재 밖에서도 복구 가능해야 하는가?

**필요하다.** 현재 암호화 백업과 복호화 수단이 모두 같은 임시 작업환경에 있어, 이 환경이 사라지면 함께 잃을 수 있다. 서로 다른 폴더에 있다는 것만으로 외부 복구가 되는 것은 아니다. 사용자가 확인한 외부 비공개 저장소는 없다. 새 유료 저장소는 만들지 않았다.

완료한 범위는 운영 앱 테이블3274행, DB에 저장한 업로드102개의 실제 바이트, 기존 서버 설정/키 보존과 로컬 격리 복원이다. 운영 앱 데이터/이미지 전체의 해시 일치와 새 스키마 적용 후 원본 불변을 검사했다. 운영 데이터로 앱을 켜거나 알림을 보내지는 않았다. 소스PG17→격리PG16이며 PG17의 MAINTAIN 권한4개는 PG16 대상에 없다. Supabase 플랫폼 전체·동일 버전 서버 완전 복원이나 외부 복구 시험으로 확대해서 해석하지 않는다.

외부 준비에 필요한 것은 다음 한 묶음이다.

- 운영자가 관리하는 **비공개 보관 위치 하나**와 읽기 권한을 가질 사람을 정한다. 기존 비공개 드라이브/저장소를 먼저 사용하며 비용이 필요한 새 서비스는 별도 판단한다.
- 암호화 백업을 그 위치에 보관하고, 복구키는 별도의 안전한 비밀 보관 수단에 둔다. 공개 GitHub·검토 ZIP·채팅에 넣지 않는다.
- 그 사본에서 내려받아 체크섬·복호화·격리 복원을 확인한다. 운영 DB에 복원하지 않는다. 작업환경 밖 사본과 키를 실제로 확인하기 전에는 ‘외부 백업 완료’가 아니다.

현재 Supabase **Backups Read / Database Read**로 백업·조회는 수행했다. 실제 새 V6 테이블/인덱스의 DDL 적용에는 읽기 권한만으로 부족하다. 운영 마이그레이션 단계에서만 BINPC2 한정 **Database Write**가 필요하다. 이번 작업에서 권한을 확대하거나 운영 SQL 쓰기를 실행하지 않았다. 기존 앱 키·VAPID·DB 주소는 유지한다.

## 개인정보 정책 — 아직 초안

관리자 ‘이력·개인정보’에서 목적별 기간·근거·정책버전·담당자/문의처를 저장하고, 별도 확인 뒤 승인하도록 기술 경로가 있다. 미확정 기간은 null이며 운영 신규 수집/파기 보호를 유지한다. 이번 작업에서 임의 확정·운영 삭제·자동 파기를 하지 않았다.

| 결정할 내용 | 권장 방향과 영향 |
|---|---|
| 신청·작성중 정보 | 행사 정리/이의 처리가 끝나면 최소화하는 기준을 정한다. 날짜만 무조건17시에 지우면 입금·당첨 후속 처리가 불가능해진다. |
| 입금·상품·정산 기록 | 거래 관련 법정 의무와 분쟁 보류를 먼저 확인한다. 일반 프로필과 보관기간을 분리한다. 자동 송금/환불은 추가하지 않는다. |
| 재사용 회원·사진 | 재사용 동의는 광고 동의와 별개다. 회원의 최종 이용일/철회 및 검토 사진의 짧은 보관·삭제 기준을 정한다. |
| 문의·관리자 이력·복구 수단 | 필요한 기간 동안 해당 담당자만 조회하고, 보안 사고/분쟁의 보류 기준도 함께 정한다. |
| 백업 | 사본 보관기간·덮어쓰기/만료·삭제요청 처리·복원 시 삭제대상 재적용 절차를 정한다. 실제 보관 장소와 담당자가 있어야 한다. |
| 승인 취소 후 노출 범위 | 현재 새 하트/메시지/입장/뽑기는 차단, 본인 기존 기록과 운영자 문의는 유지한다. 다른 참가자 목록에서 숨기기·기존 대화 읽기/수신까지 제한할지는 별도 운영정책이다. |

## 기존 Netlify·Render 반영 준비

1. 외부 복구 조건과 최종 CI·동일 코드 지문을 확인한다. 현재 서비스는 계속 기존main 버전이다.
2. 모집을 열지 않는 호환 스키마를 백업된 기존DB에 적용할 순서·권한을 확인한다. 신규 테이블/인덱스 추가는 기존 데이터 삭제/키 교체와 다르다. 세션·원장 키를 바꾸지 않는다.
3. 기존 서비스에 같은 검증 소스의 API/화면을 반영하되 신규 모듈 OFF, **테스트ON / publicAdmissionOpen=false**를 확인한다. main 병합/새 사이트를 만들지 않는다. 이전 배포ID와 기존 설정을 보존한다.
4. 배포ID·실행SHA/지문·신청 API 거절·기존프로필/PIN 복구·하트/채팅·지도 권한·관리자 시험실을 기존주소에서 검사한다. 가상 데이터는 시험실 저장소에만 쓴다.
5. 문제 시 신규 접수를 계속 닫고 기능을 OFF한다. 데이터/키는 보존한 채 호환되는 이전 API/화면으로 되돌린다. 운영DB를 초기화하지 않는다.
6. 보스가 테스트 후 실제 오픈을 명시 확인해야 모집을 연다. 테스트OFF는 오픈 승인이 아니다. 개인정보 정책 승인과 웹/오픈채팅 모집 오픈도 구분한다.

## 배포 후 보스가 확인할 순서

기존 `https://binpc2.netlify.app` → 관리자 로그인 → **술번개 → 행사 설정·기록·관리 도구 → 선착순 시험실**. 금/토·가상3등·입금신고/승인·프로필 일부/완료·입장·카드/상품을 눌러본다. 초기화는 시험실 기록만 지운다.

갤럭시·아이폰 각각에서 시험실/승인된 확인용 계정으로 프로필/PIN을 적어 두고, 은행 앱/카카오톡 이동·잠금해제·새로고침·네트워크 단절/복귀 후 같은 프로필·하트·대화가 복구되는지 확인한다. 실제 참가자 계정이나 송금으로 시험하지 않는다. 17시 정상 종료된 현장 프로필의 복원을 요구하지 않으며 신청/입금/당첨 원장은 별도로 남아야 한다. 실물폰·푸시·모바일 키보드는 아직 UNKNOWN이다.

**이 안내는 배포 이후의 순서다. 현재 기존 사이트에 이번 V12가 반영됐다는 뜻이 아니다.**
