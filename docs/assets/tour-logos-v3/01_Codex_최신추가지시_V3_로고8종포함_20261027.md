## 이번 정정의 우선순위

사용자는 이전 전체 할로윈·전국투어·모듈형 지시문을 이미 Codex에 보냈다. **이 파일은 직전 추가 지시문을 대체하는 최신 정정본**이다. 새 작업을 만들거나 기존 전체 지시를 처음부터 다시 실행하지 않는다. 충돌하는 부분만 이번 사용자 결정으로 갱신하고 나머지 누적 요구는 모두 유지한다.

1. 할로윈 금요일 22:30 시작, 토요일 22:00 시작, **두 날 모두 다음 날 01:00 종료**. 예전 토요일 00:30 종료 문구는 현재 할로윈 설정으로 사용하지 않는다.
2. 테마·기존 참가자 뽑기 유효기간은 각 회차 다음 날 17시 초기화까지. 실제 술자리 종료·새 입장 마감과 구분한다.
3. 상품·상금·할인 기록용 전화번호는 **입력하고 저장만** 한다. SMS/전화 인증·새 비밀번호·별도 본인확인·번호 수정 승인 절차를 추가하지 않는다. 지급 전 운영자가 직접 더블체크한다. 기존 프로필 재사용용 선택 비밀번호 정책은 별개로 유지한다.
4. **현재 갤럭시와 아이폰에서 프로필/참가자 화면이 첫 화면으로 돌아가는 실사용 오류를 최우선(P0)으로 조사·수정·재검증**한다. 신청기록 복구만으로 해결 완료라고 하지 않는다.
5. 이번 ZIP에는 **7개 매장 + 고래 감사용, 총 8종의 실제 이미지 파일**이 있다. 다른 대화의 Library에서 원본을 실제 복구·열람했으며, 앱용 이미지와 원본·체크섬을 함께 전달한다. ‘온탑만 수령 / 다른 로고 없음’이라는 앞선 설명은 현재 수령 상태가 아니다. 파일 전달과 실제 앱 연결 완료는 구분한다.
6. 수정·개발 지시는 같은 Codex 작업에서 이어간다. 기존 디자인 보호·예약접수·늦참·관리자 결과 보고·성능/보안 검사·안전한 정리는 모두 유지한다.

## 0. 기존 작업 유지 및 실행 경계

사용자는 직전 할로윈·전국투어·모듈형 전체 지시문을 이미 보냈다. 새 작업/새 프로젝트를 만들지 말고 같은 Codex 작업에 이 추가 지시를 이어 적용한다. 여기서 명시적으로 바꾼 규칙만 최신으로 덮어쓰고, 기존의 나머지 요구를 모두 유지한다.

기존 V6 신청·저장 영수증·재접속·입금 수동승인·개인 대기방·프로필·관리자 문의·회귀검사를 재사용한다. 완료 기능 재제작, 전체 디자인 교체, 정상 기능 삭제 금지. 다른 작업자·미커밋 변경·브랜치 충돌을 확인한다. main 기준으로 되돌아가거나 정책 초안 V7 전체를 병합하지 않는다.

이번 목표는 내일 예정된 접수를 위한 정확성·복구·실시간·속도 검증까지다. 배포 완료를 추정하거나 무오류를 보장하지 않는다. 실제 모집 공개·운영 배포·운영 개인정보 파기·외부 발송·과금·Secret 변경은 기존 승인 경계를 지킨다. 개발 브랜치 저장 승인은 운영 공개 승인이 아니다. 예약값은 현재 ‘예정값’으로 기록하며, 운영 공개 조건과 승인이 충족된 뒤 예약을 활성화한다.

금요일 17시에는 금요일 회차만 만료한다. 그 처리로 토요일 할로윈 방이나 다음 주 대기방의 테마·접수·기록을 끄면 안 된다.

기존 초기화 시계의 서버 기준 만료시각을 재사용하고 별도 상충 타이머를 만들지 않는다. 자정 뒤 접속도 시작 날짜의 행사 ID에 연결한다. 서버 재시작·백그라운드 복귀 때 종료 여부를 다시 계산한다. 종료된 할로윈 설정이 다음 일반 술번개나 전국투어로 복사되지 않게 한다. 관리자의 개별 테마 OFF도 지원하며 OFF는 기록 삭제가 아니다.

## 3. 선착순 신청 시간 설정과 자동 접수 ON

관리자 ‘행사·자동방 → 해당 술번개 → 모집 일정’에 아래 항목을 둔다.

- 접수 방식: 즉시 수동 / 날짜·시간 예약.
- 신청 시작 날짜·시간, 모집 종료 날짜·시간(선택), 선착순 혜택 시작·종료 조건.
- ‘예약시각에 신청 자동 시작’ ON/OFF.
- ‘저장’, ‘예약 미리보기’, ‘예약 일시중지’, ‘즉시 접수 중지’, ‘처리 이력’.

현재 예상 기본값:
- 금요일 10/30 할로윈: 2026-10-28 수요일 20:00 KST에 신청 시작 예정.
- 토요일 10/31 할로윈: 2026-10-29 목요일 20:00 KST에 신청 시작 예정.

운영자 수정 가능한 예정값으로 등록한다. 모든 준비·운영 승인이 끝나 한 번 예약을 활성화하면 정해진 시각에 자동으로 모집 중 상태가 되어야 한다. 매번 운영자가 다시 눌러야 하는 수동 운영으로 되돌리지 않는다.

한국시간 서버 시계를 기준으로 정확히 20:00 이전 신청 확정/혜택 순번 확보를 거부한다. 사전 안내·미리입력·임시저장이 있더라도 정식 접수나 선착순 자리를 먼저 차지하지 못하게 한다. 모바일 시계 변경·새로고침·직접 API 요청도 같은 판정이다. 참가 화면은 ‘신청 시작 예정 / 남은 시간’에서 접수 가능 버튼으로 갱신한다. 시각 도달만으로 새로고침을 강제하지 않는다.

예약 실행은 재시작/여러 인스턴스에서도 중복하지 않는다. 사용자가 화면을 열지 않아도 실행하며, 읽기 시 서버의 예약 상태 확인으로 지연된 작업을 보정한다. 모집 시작 작업은 저장 성공 뒤 관리자 이력/알림함에 남긴다. 이미 정지·취소한 예약을 서버 재시작이 다시 켜지 않게 한다.

기존 recruitment + opensAt 구조를 먼저 검사한다. 현재 확인된 운영 코드의 무조건적인 production 접수 차단을 단순 삭제하지 않는다. 실제 확정 정책·필수 설정·운영자 승인 상태를 검증하는 명시적인 준비조건으로 바꿀 수 있도록 구현하고, 미승인 상태의 기본 차단과 이유 표시를 유지한다. 개발 중 production 모드를 development로 바꾸어 보호를 우회하지 않는다.

최소 5명 규칙은 ‘실제 개최 준비조건’이지 첫 접수를 막는 조건이 아니다. 0명이어도 검증된 모집을 시작할 수 있어야 한다. 토요일 자동방 ON/OFF, 개별 방 모집 예약, 기존 회식 시작은 서로 다른 스위치다.

## 4. 늦참 신고·도착 예정시각·관리자 개입

참가자 신청 화면과 개인 대기방에 ‘늦게 도착해요 / 도착 예정시간’ 버튼을 둔다. 누르면 해당 날짜와 시·분, 간단 사유(선택), 빠른 선택 문구가 나타나는 아래쪽 창 또는 접이식 입력란을 연다. 모든 선택은 저장 중→서버 성공→저장 완료 표시 후 반영한다.

할로윈 안내는 실제 행사 시간에서 생성한다.
- 금요일: ‘이번 술번개는 1차만 진행하며 다음 날 01:00에 종료됩니다. 2차는 없습니다. 늦게 도착하셔도 본인에게 안내된 회비는 동일합니다. 도착 예정시간을 확인하고 1차를 신청해 주세요.’
- 토요일: ‘이번 술번개는 1차만 진행하며 다음 날 01:00에 종료됩니다. 2차는 없습니다. 늦게 도착하셔도 본인에게 안내된 회비는 동일합니다. 도착 예정시간을 확인하고 1차를 신청해 주세요.’

예정 도착시각·종료시각·남은 이용시간을 짧게 보여주고 ‘내용 확인’, ‘도착시간 저장’, ‘관리자에게 문의’를 제공한다. 기존 확정 회비나 선착순 혜택을 늦참 표시만으로 재계산하지 않는다. 신규 참가자의 회비는 기존 공식 가격정책으로 정하고 시간 비례 할인은 만들지 않는다.

너무 늦은 시간의 기준은 운영자가 설정하거나 개별 판단한다. 임의의 자동 탈락 분수를 만들지 않는다. 종료시각 이상 도착, 날짜/차수 혼동, 관리자가 설정한 늦참 검토조건이면 ‘관리자 확인 필요’로 연결하고 관리자가 대화에서 승인/불가/다른 날짜 안내를 할 수 있게 한다. 아직 입금 전인 신규 신청에는 검토 중임을 명확히 보이고 잘못된 자동 납부 유도를 막는다. 이미 입금한 기존 신청은 새 신청을 만들거나 기존 승인을 지우지 않는다.

관리자 신청 카드에는 예정 도착, 늦참 상태, 사유, 대화 버튼과 승인 내역을 표시한다. 자동 시스템 메시지와 관리자 답장을 구분한다. 앱을 잠시 닫거나 답장이 늦다는 이유만으로 노쇼·퇴장 처리하지 않는다.

‘2차는 없습니다’는 할로윈 1차 전용이다. 전국투어는 1차 BINPC2, 2차 외부 오픈채팅, 3차 현장 안내라는 기존 구분을 유지한다. 2차 링크가 아직 없으면 임의 링크나 자동 2차 신청을 만들지 않는다.

## 5. 전화번호는 입력만 — 상품·상금·할인 기록과 관리자 더블체크

**참가자 동작: 전화번호 입력(기존 값이 있으면 자동 채움) → 저장 → 관리자 결과목록에 표시. 끝.**

- 이 전화번호 입력·저장 때문에 SMS 인증, 전화 인증, 추가 비밀번호, 신분 확인, 운영자 번호등록 승인이나 번호수정 승인 절차를 새로 요구하지 않는다.
- 운영자가 실제 지급 전에 더블체크한다. 전화번호는 지급 자동승인·본인 인증 완료 표시가 아니다.
- ‘다음에도 프로필 사용’ 체크 시만 설정하는 기존 선택 비밀번호는 계정 재사용 기능이다. 혜택용 전화번호 저장과 묶어 필수화하지 않는다.
- 본인 신청/프로필 세션에서 번호를 저장·수정한다. 기존 서버 권한검사는 화면 뒤에서 유지하고, 일반 번호 입력 과정에 새로운 확인 단계를 늘리지 않는다.
- 동일 전화번호가 입력돼도 다른 사람의 과거 신청·상세주소·대화·상품 소유권을 자동으로 넘기거나 자동 병합하지 않는다. 중복/오타 의심은 관리자에게 참고 표시하고 운영자가 판단한다.
- 사용자에게 전화번호만 입력시키는 것과, 번호를 아는 누구에게나 과거 개인정보를 공개하는 것은 별개다. 참가자는 자기 세션의 기록만 보고, 전체 번호검색·과거 지급기록 대조는 관리자 전용으로 둔다.

내부 기록 기준은 변하지 않는 회원 ID·신청 ID·행사 ID다. 전화번호는 관리자 검색·대조용으로 연결한다. 닉네임 변경이나 현장 17시 초기화로 소유자가 바뀌면 안 된다. 다음 행사까지 보관하는 것은 기존 재사용 동의·목적별 보관정책 범위 안에서만 한다.

관리자 ‘경품·상금·할인 결과’에 행사/날짜, 닉네임, 전화번호(기본 마스킹·권한 있는 관리자 상세 열람), 결과·금액, 지급 또는 확인 상태를 표시한다. 번호·닉네임·행사 검색을 제공한다. 전체 번호를 일반 알림·공개 URL·오류로그·GitHub에 기록하지 않는다.

할로윈 실물 상품, 전국투어 할인권 금액, 선착순 무료/할인, 운영자가 직접 입력한 상금 결과를 전부 관리자에게 보고한다. 전국투어 기본목록의 ‘닉네임: 당첨/꽝’은 간단히 유지하고 상세에서 실제 금액을 본다.

서버 저장이 끝난 결과만 보고한다. 같은 요청을 재전송해도 결과·지급 확인은 중복하지 않는다. 수신 확인과 실제 지급 확인은 분리한다. 운영자는 지급 전에 직접 더블체크하며, 시스템이 전화번호만 보고 자동 지급하지 않는다.

최종 1/N 정산·추가 납부 계산·자동송금·환불 프로그램·무작위 현금 추첨은 만들지 않는다. 과거 10만원 상금 예산을 현재 확정 경품으로 자동 복구하지 않는다.

## 6. 돈 관련 범위 재확인

할로윈은 기존 확정 가격표에 따른 선입금 또는 관리자 무료 승인, 전국투어는 관리자가 입력한 선입금만 처리한다.

최종 1/N 정산, 추가 납부액 계산, 환불 처리, 자동송금, 실제 은행 자동조회, 카드결제는 추가하지 않는다. 소유자별 상품·상금·할인 결과 조회는 정산 프로그램과 별개다.

할로윈 1등 무료는 payment approved에 가짜 송금을 만들지 말고 별도 면제 승인 증거로 처리한다. 상세 장소는 실제 입금승인 또는 적법한 관리자 무료 참가 승인 후 해당 참가자에게만 공개한다. 사전신청/무응답 혜택 승계, 확정 회비·과거 기록 보호는 기존 최신 지시를 유지한다.

## 7. P0 — 갤럭시·아이폰 프로필이 첫 화면으로 돌아가는 실사용 오류

**사용자가 현재 갤럭시와 아이폰에서 프로필/참가자 화면이 계속 첫 화면으로 돌아간다고 직접 보고했다.** 이것은 ‘나중에 실기기로 보면 되는 항목’이 아니라 현재 조사·수정해야 할 최우선 결함이다. 신청 데이터 보존만 확인하거나 과거 테스트 숫자를 제시해서 해결됐다고 하지 않는다.

### 7-1. 정상 동작

- 같은 행사 주기에서 정상 등록·입장한 참가자는 화면 잠금/잠금해제, 다른 앱 전환, 카카오톡 또는 은행 앱 확인, 브라우저 백그라운드/복귀, 탭 재열기, 새로고침, 통신 단절/복구 후에도 기존 프로필·닉네임·고유번호·하트 사용·채팅 상태를 복원한다.
- 프로필 작성 도중이라면 기존에 저장한 단계와 값을 복원한다. 입장 전 프로필은 공개하지 않는 기존 규칙을 유지한다.
- 기록을 불러오는 중이거나 일시적으로 읽기에 실패한 것을 ‘프로필이 없음’으로 처리해 첫 화면·신규 등록 화면으로 보내지 않는다.
- 복구 중에는 기존 화면을 유지하거나 ‘연결 확인 중 / 기존 프로필을 불러오는 중’과 재시도·관리자 문의를 제공한다. 사용자의 현재 ID나 인증수단을 먼저 지우지 않는다.
- 복구가 필요한 상황이어도 기존 사람으로 돌아와야 한다. 새 프로필/새 고유번호 생성, 카드·하트 횟수 초기화, 중복 입금 요구는 금지한다.
- 고의 로그아웃, 유효한 관리자 종료, 올바른 행사주기의 실제 17시 초기화 같은 정상 종료와 오류를 분리한다. 17시가 지나면 끝난 현장 프로필을 무단으로 되살리지 않되, 별도 신청·입금·당첨 기록은 개인 신청내역에서 유지한다.

### 7-2. 먼저 실제 원인 확인

운영에 실제 배포된 버전과 현재 V6 개발 브랜치를 분리해 조사한다. 현재 운영 사이트에서 발생한 문제를 V6 시험환경만 보고 해결됐다고 단정하지 않는다. 운영은 승인된 안전한 읽기만 하고, 수정은 격리 개발환경에서 먼저 한다.

기존 profile-session, App/bootstrap, 입장 게이트, 닉네임 등록/복구, 세션 갱신, localStorage/sessionStorage/쿠키, SSE 재연결, 오래된 ready 응답, reset_signal·행사 cycle 검사, 서비스워커 업데이트, 강제 reload/navigation, 프로필 완료 판정 경로를 확인한다. 이 목록은 확인 후보이며 원인으로 확정한 사실이 아니다.

특히 다음을 확인한다.
1. 로딩 중 null/빈 응답/timeout/일시 5xx를 미가입으로 처리하는가.
2. 네트워크 실패 시 userId·profileId·PIN·device secret·복구수단을 지우는가.
3. 오래된 응답·취소된 요청이 최신 프로필/입금승인/현재 route를 덮어쓰는가.
4. 앱 복귀 또는 service worker 업데이트가 강제 새로고침·첫 화면 이동을 유발하는가.
5. 저장소 차단이나 세션 갱신 경합 때 복구 가능한 서버 기록을 무시하는가.
6. 잘못된 날짜/행사주기의 초기화 신호 또는 중복 수신이 정상 프로필을 만료시키는가.
7. 새 V6의 인증·복구·기본 프로필 검증 변경이 기존 참가자에게 회귀를 일으켰는가.

화면 전환의 이유코드·응답상태·순서·행사주기만 최소한으로 추적한다. 전화번호·실명·PIN·비밀번호·세션 토큰·기기 비밀값 원문을 로그나 화면 캡처에 넣지 않는다. 보호 검사를 제거해 강제로 메인에 넣는 우회 해결은 금지한다.

### 7-3. 수정과 재발 방지 검사

- 원인 확인 → 최소 수정 → 재현 실패조건 자동검사 추가 → 기존 기능 회귀검사 → 실제 앱 화면 재검증.
- 기본 프로필+채팅+하트를 유지한 상태에서 잠금/복귀·은행 앱 이동·재접속·실패 응답·응답 순서 뒤바뀜·API 재시작·저장소 예외를 조합해 검사한다.
- Chromium과 가능한 WebKit 검사, Android/iOS 브라우저별 복구 흐름을 확인한다. 실제 갤럭시/아이폰이 없는 환경의 브라우저 시험을 실기기 PASS로 기록하지 않는다.
- 접근 가능한 실제 갤럭시 Chrome/Samsung Internet과 iPhone Safari/PWA에서 OS·브라우저·접속방식별로 검증한다. 실기기 접근이 없다면 코드/격리검사는 계속 완료하고 실기기 확인만 별도로 남긴다.
- 전체 페이지 새로고침 반복·무제한 재접속·보안 만료 폐지·복구코드 공개로 해결하지 않는다.
- 완료 보고에는 문제를 재현한 조건, 직접 확인한 원인, 수정 파일, 전후 결과, 기기별 실제 검사 범위를 분리한다.

### 7-4. 기존 신청·입금 안정성도 유지

각 단계 서버 저장 후 다음 화면, 저장 영수증 우선 조회, 같은 요청 중복방지, 오래된 응답 거부, 관리자 승인 보존을 유지한다. 브라우저가 종료되더라도 저장된 신청·입금·프로필·대화·당첨 기록은 같은 신청으로 복구한다. 보안상 재인증이 정말 필요한 경우 기존 계정을 복구하고 새 신청을 만들지 않는다. 상품 기록용 전화번호 입력에 이 재인증을 붙여 추가 절차로 만들지는 않는다.

## 8. 공지 표현 변경

신규 공개용 공지·기본 템플릿에서 사용자가 삭제 요청한 ‘성희롱’이라는 단어를 제외한다. 원문/과거 버전은 역사로 보존한다.

대신 기존의 기본 예절·무단촬영·불쾌한 언행·원치 않는 접촉·강요·폭력 금지 안내와 관리자 대응 기능은 유지한다. 예시 기본 문구: ‘욕설·비하·폭력·무단촬영·원치 않는 언행이나 신체접촉·진행 방해는 금지합니다.’

운영자 근무·숙면 중 응답 지연 안내, 늦참 회비 동일, 관리자 확인 지연으로 정상 송금자 불이익 금지는 그대로 유지한다. 공지 수정으로 확정된 금액을 바꾸지 않고 재동의가 필요한 중요 변경만 구분한다.

## 9. Codex 자동검사와 운영자 점검 화면

기존 ‘선착순 시험실’을 실제 화면 컴포넌트를 재사용해 확장한다. 새로운 독립 HTML 체험판은 만들지 않는다.

관리자 ‘운영 점검’에 저장·이어하기·예약접수·늦참·입금/무료승인·전화번호별 혜택·실시간·속도·17시 테마 복원·모듈 OFF/ON 검사를 구분한다. 테스트 환경 표시, 대상 행사, 선택 순위, 마지막 검사 시각, 실제 결과와 실패 이유, 안전한 재시험 버튼을 제공한다. 버튼을 눌렀다는 이유만으로 PASS를 만들지 않는다.

사용자가 3등으로 들어가 참가자 화면을 확인할 수 있어야 한다. ‘신청 시작 직전/정각’, ‘도착예정 23:30/종료직전/종료이후’, ‘입금신고/승인완료’, ‘테마17시전/후’를 선택한다. 시간 조작·가상 입금·부하발생은 시험환경에만 허용한다.

시험실 조작은 운영 시계·실제 참가자·실제 경품·계좌·개인정보·발송에 영향을 주지 않는다. 운영 관리자는 비파괴적인 준비상태와 실제 알림 지연만 볼 수 있다. 대량 요청·시간변경·파기는 격리 환경에서 실행한다.

Codex는 다음을 자동검증한다.
1. 2026-10-28/29 19:59:59 접수 거절, 20:00:00 접수 허용, 서버 재시작/중복 실행/수동 중지 유지.
2. 예약 시작과 21시 당일 할인 마감, 선착순 혜택, 사용자 재접속이 서로 다른 상태를 덮어쓰지 않음.
3. 두 할로윈 회차의 실제 종료와 17시 이벤트 만료 분리, 새 회차 오염 없음.
4. 100명 동시 신청·중복 클릭, 여유부하 150명, 신청+입금승인+문의+뽑기 혼합 부하.
5. 저장 성공 후 응답 유실, 탭 종료, 로그아웃/복구, 다른 브라우저, 인터넷 재연결, API 재시작.
6. 늦참 날짜·차수·종료시각·동일 회비·관리자 검토·이미 입금한 신청 보호.
7. 혜택용 전화번호 입력/수정/저장에 SMS·추가 비밀번호·새 본인확인 없음, 관리자 더블체크와 결과조회, 동일번호 자동병합/타인 기록노출 금지, 기존 소유권 유지.
8. 상품/할인/상금 수동기록의 관리자 보고 누락0·중복0, 결과 확인과 실제 지급 구분.
9. 실제 React+API+격리 PostgreSQL에서 금23/토49 재고, 전국투어 2장 중1장 당첨, 기존 전체 회귀검사.
10. 320/360/390/768/1024px, 밝음/어두움, 키보드·뒤로가기·문의창·버튼 겹침 검증. 갤럭시·아이폰의 첫 화면 복귀 문제는 7절 P0 재현/수정검사를 별도로 수행한다. 실제 물리 기기를 쓰지 않은 항목은 실기기 UNKNOWN으로 남긴다.
11. 실시간 문의·입금승인·혜택승계·예약접수 갱신. 여러 창에서 메시지 순서·재연결·읽음·중복 리스너·중복 SSE 검사.
12. 장시간 세션 유지·메모리·연결 수·요청 수·DB 잠금 경합·업로드/영상 스트리밍 검사. 실제 실행한 지속시간을 보고하고 장시간 테스트 완료를 꾸미지 않는다.

속도는 현재값을 측정하고 동일 조건의 개선 전/후로 보고한다. 잠정 목표는 버튼 반응100ms 이내, 100명 부하에서 저장/승인 응답 95%가2초 이내, 활성화면 상태전파95%가2초 이내다. 초기 화면/영상은 기기·네트워크 조건을 기록하고 목표를 별도로 세운다. 이 수치는 목표이며 현재 성적이 아니다. 기준 미달을 감추거나 보안검사를 빼서 속도를 높이지 않는다. 긴 전역 DB 잠금이 병목이면 트랜잭션 정합성을 보존한 최소 수정만 검토한다.

실시간은 기존 연결방식을 재사용하고 화면 전체 1초 주기 새로고침/무제한 폴링을 추가하지 않는다. 활성화면 전달과 휴대폰 앱종료 푸시는 별도 성적이다. 실제 푸시는 미승인 발송하지 않고 로직/가상전송 검증 후 기기 확인 사항만 남긴다.

## 10. 코드·파일 용량 정리 및 안전한 최적화

먼저 파일별 용량, 실제 참조, 산출물, 의존성, 네트워크 로딩량을 조사한다.

정리 후보는 개발환경에서 재생성 가능한 임시파일·캐시·중복 빌드·명확히 미사용 코드·실수로 포함된 소스맵/대형 데모다. ‘과거’ 또는 ‘warning’이라는 이유만으로 삭제하지 않는다.

원본 로고, 사용자 업로드, 최초/최신 정본, DB 백업, Git history, 테스트, 실패증거, 복구코드, 암호화키, 기존 정상기능을 쓰레기로 취급하지 않는다. 다른 프로젝트나 PC 전체를 정리하지 않는다. 강제push·Git이력 축소·무작정 npm 의존성 업데이트·대규모 리팩터링 금지.

선별한 임시 산출물은 재생성/복구 가능한지 확인한 뒤 개발영역에서만 삭제할 수 있다. 중요한 검증자료는 검증된 다른 보존처가 있는지 확인한 뒤 정리 후보로 분리한다. 오래된 HTML은 새로 개선하지 말고 보존용 자료와 실제 앱 배포 파일을 분리한다. 실제 사이트 초기 로딩에 데모 ZIP/시험영상/검토자료가 끼지 않게 한다.

정리 전후 용량(MB), 제거 경로, 근거, 복구 방법, 영향범위·회귀검사를 보고한다. 단순 압축으로 서버 저장안전·보안·기존 디자인을 훼손하지 않는다.

## 11. 내일 접수 준비 대시보드와 차단조건

현재 원격 코드에는 운영 모집/신규 신청의 production 차단이 남아 있다. 완료율이나 과거 테스트 개수만으로 내일 접수가 가능하다고 말하지 않는다.

관리자에게 아래 준비조건을 확인 가능한 상태로 보여준다.
- 최신 추가 규칙 구현/검증 결과.
- 개인정보 정책 버전·목적별 보관/파기·사진/연락처·운영책임 정보 검토 상태.
- 실제 적용 회비/무료승인/계좌/입금 안내의 준비 상태. 실제 값을 코드/공개로그에 넣지 않음.
- 예약 시작시각과 자동ON 승인 상태.
- 코드와 운영 DB 변경계획, 백업·복구 확인.
- 운영자 기기/참가자 실제 화면 리허설 범위와 미검증 항목.
- 네트워크·저장 실패 복구와 문의 전달 가능 여부.
- 기능OFF/긴급접수중지/되돌리기 절차.

개인정보 정책 미확정과 실제 배포 미승인을 감추거나 차단을 우회하지 않는다. 자동으로 할 수 있는 준비·개발·검증은 계속하고, 운영자가 결정해야 하는 필수 선택만 쉬운 문장으로 한 번에 모아 보고한다. 이미 확정된 선입금 방식·차수별 매장 배정을 다시 질문하지 않는다.

공개 승인 후 운영 예약을 활성화하면 수동 클릭을 다시 요구하지 않는 완전자동 시작을 목표로 한다. 현재 계획서 작성만으로 운영 예약이 저장·활성화됐다고 말하지 않는다.

## 12. 완료보고·GitHub 저장·계속 작업

기존 브랜치에서 P0 모바일 프로필 복귀 문제 원인분석→필요한 부분 수정→자동시험→실패수정→재시험→나머지 예약/행사 요구 연결→실제 앱 화면 검증→정본/상태기록을 이어간다. 개발범위를 날짜별로 쪼개 사용자에게 매번 다음 지시를 요구하지 않는다. 코드 변경 전후 최신 git 상태를 확인한다.

완료된 안전한 개발 변경은 기존 승인 범위에서 개발 브랜치에 커밋·Push하고 원격 SHA를 확인한다. main 병합·운영 배포·Netlify Stopped builds/Render 설정 변경·실제모집·광고발송·운영 개인정보 삭제·Secret교체는 별도승인 경계를 유지한다.

최종 보고:
- 최우선: 갤럭시·아이폰 첫 화면 복귀의 확인된 원인, 수정 범위, 프로필/고유번호/하트·채팅/입금 기록 보존 시험, 실제 기기와 브라우저 모의검사 구분.
- 이번 추가규칙의 구현/검증/미완료 표와 최신 SHA.
- 예약 접수 두 날짜, ON/OFF 상태, 공개가 가능한지/막힌 이유.
- 17시 테마·뽑기 만료와 현장 초기화/신청원장 보존 시험.
- 늦참 정상/늦은시간 관리자개입 실제 화면.
- 관리자 혜택결과·전화번호 검색과 타인조회 차단.
- 성능 전후 수치, 재접속/혼합부하/실시간 결과, 물리기기 미검증 구분.
- 제거한 불필요한 파일/용량/복구방법.
- 8종 로고의 실제 파일/앱 연결 상태·원본/추출본/제작시안 구분·최신 JACK 여부. 파일 확보를 실제 배포 완료라고 표시하지 않음.
- 실제 React·Express·격리 DB에서 얻은 화면·짧은 검증녹화.
- 사용자에게 필요한 마지막 정책/운영승인만 한 번에 정리.

핵심: 내일부터 신청을 받을 수 있도록 가능한 기술 작업은 모두 이어가되, 참가자가 이미 보낸 돈과 신청정보를 지키는 검사를 생략하지 않는다. 테스트·보고서·개발브랜치 저장과 운영공개는 구분한다.


## 13. 이번 V3 변경 이력과 승인 경계

- 앞선 답변에서 다른 로고를 미수령으로 단정했던 오류를 실제 Library 원본 열람·복구로 정정했다.
- 온탑 외 레드홀·페이크·자크·M가라오케·스피드·체크인·고래의 실제 이미지 파일을 확보했다.
- 원본 8개 보존과 앱 연결용 8개, 원본추적 JSON, 체크섬, 미리보기, 지시문을 묶었다. 같은 도안의 원본/추출본을 중복 도안 수로 세지 않는다.
- 할로윈 금·토 모두 01시 종료, 혜택용 전화번호 입력만, 모바일 프로필 복귀 오류 최우선, 17시 테마/이벤트 만료, 예약접수·늦참·관리자 보고·검증·정리 요구를 유지한다.
- 사용자에게 같은 로고를 다시 업로드하라고 요구하기 전에 이 ZIP의 8개 실제 자산부터 사용한다.
- 이 자료를 만든 현재 대화에서는 저장소/코드/운영 설정을 변경하지 않았다. 실제 구현과 검증은 기존 Codex 작업에서 이어가며 운영 공개는 별도 승인 경계를 유지한다.
