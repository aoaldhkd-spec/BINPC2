## 3. 보호 백업에 반드시 들어갈 것

| 대상 | 현 코드의 저장 경로 | 복원 확인 |
|---|---|---|
| 기존 프로필·하트·채팅·설정·기기 인증·운영 이력 | PostgreSQL `app_kv_rows` 및 실제 운영의 기존 관련 테이블 | 테이블·종류별 건수와 내용의 비공개 해시, 필요한 계정·참가 상태의 일치. 실제 행을 보고서에 출력하지 않는다. |
| 기존 프로필·채팅 사진 | `app_image_store.data_url` | 원본 바이트·개수·비공개 해시와 관련 기록 연결. 화면 캡처만 보존한 것을 원본 백업으로 보지 않는다. |
| V6 신청·입금·문의·당첨·지급·테스트 원장 | `event_hub_records` | 종류별 건수, 인증된 복호화, 신청·입금·당첨 관계와 기록 revision 보존. |
| V6 공지·지도·영상·새 로고 | `event_hub_records`의 `settings` / `media:*` 암호화 기록 | 복호화한 파일 바이트·원본 해시·행사 연결·권한 메타데이터. |
| 로그인 세션 | `app_sessions`와 관련 기존 인증 기록 | 동일 키·세션 설정을 유지하는지 확인. 백업을 위해 모든 사용자의 로그인 정보를 재발급하지 않는다. |
| 현재 운영에서 추가로 사용하는 업로드 저장소 | 연결 후 실제 디스크·외부 저장소 설정 확인 | 현재 코드의 DB 저장 경로만 보고 운영에 별도 저장소가 없다고 단정하지 않는다. |
| DB 스키마·인덱스·권한·RLS | 실제 운영 PostgreSQL 정의 | 데이터만 복원하고 권한이 빠지지 않았는지 확인. 공급자 전용 역할은 복원 환경에 맞게 검토한다. |
| 기존 운영 키·설정 | 보호된 서비스 설정/비밀 보관소 | DB 덤프와 분리해 보호 보관하고 복원 권한자·보관 위치·복원 확인 시각만 기록한다. |

원장 암호화 키는 `SESSION_SECRET`에서 HKDF-SHA256으로 파생된다. 코드의 salt는 `binpc2-event-hub-v6`, info는 `private-records`이며 원장은 AES-256-GCM을 사용한다. 따라서 같은 DB라도 다른 `SESSION_SECRET`으로는 기존 원장을 정상 복호화할 수 없다. **키가 없으면 새 키로 덮어 해결하지 않는다.** 기존 세션·HMAC 복구 관계와 `VAPID` 등 다른 운영 인증 설정도 보존한다. 외부 알림 검사를 명목으로 발송하거나 관련 키를 교체하지 않는다.

덤프 자체에 개인정보와 기존 이미지가 들어갈 수 있으므로 접근이 제한된 암호화 보관을 사용한다. 덤프·평문 개인정보·암호화키를 공개 소스·검토 ZIP에 넣지 않는다. 백업 파일명·크기·체크섬·생성 시각·암호화 여부·복원 결과 등 필요한 증거만 공개 가능한 보고서에 남긴다.

### 완전 백업으로 사용할 수 없는 것

- Git bundle, 소스 ZIP, Git 태그는 코드 복구 자료다. 운영 DB·업로드·키 복원 증거가 아니다.
- 기존 관리자 데이터 JSON 내보내기는 일부 행수 제한과 비밀번호 마스킹이 있으며 V6 원장·이미지 저장소·세션 전체를 포함하지 않는다. 이것만으로 완전 복원을 선언하지 않는다.
- `scripts/backup-checkpoint.mjs`는 main 태그·Push 도구다. 이번 작업에서 DB 백업 명목으로 실행하지 않는다.
- `security-harden.mjs`, `rotate-secrets.mjs`, `rotate-exposed-secrets.mjs`는 운영 비밀값 변경을 포함하므로 이번 배포 절차에 사용하지 않는다.
- `render.yaml`의 `SESSION_SECRET generateValue: true`는 기존 운영 키 재생성을 지시하는 절차로 사용하지 않는다. 새 Blueprint·서비스를 만들지 않는다.

## 4. 격리 복원과 스키마 확인 순서

1. 기존 서비스 ID·현재 배포 ID·코드·실제 DB 대상·업로드 경로를 읽기 전용으로 확인한다. 다른 운영 DB나 개발 DB를 잘못 백업하지 않도록 대상을 대조한다.
2. 운영 데이터를 변경하지 않는 일관된 DB 백업과 업로드 보존본을 만든다. 동일한 기존 키는 별도 보호 보관한다. 실제 적용 전에 백업의 읽기 가능성과 체크섬을 확인한다.
3. 기존 격리 환경의 복원용 PostgreSQL에 복원한다. 운영 DB 접속값을 시험 실행에 그대로 전달하지 않는다. 외부 발송과 운영 서비스 쓰기 경로는 연결하지 않는다.
4. 앱 전체 부팅 전에 SQL·복호화 검사를 먼저 수행한다. 서버 시작 과정과 17시 초기화가 복원본을 바꿀 수 있으므로 단순히 앱이 켜진 것만으로 복원 성공을 판정하지 않는다. 기존 기록·업로드 바이트·키 일치와 삭제/철회 기록 보존을 확인한다.
5. 복원본에서 최신 스키마와 호환되는지 확인한다. `artifacts/api-server/migrations/20261027_event_hub.sql`은 원장/인덱스와 `laboratory-mode`, `laboratory-workspace` 허용을 포함한다. 일반 production 서버 시작은 이 migration을 자동 적용하지 않는다.
6. 해당 SQL의 CHECK 제약 교체는 트랜잭션과 잠금 영향을 고려해 수행한다. 제약을 삭제한 뒤 추가하지 못한 상태를 남기지 않는다. 원장이나 기존 업무 데이터를 삭제·초기화하지 않는다. RLS와 공개 역할 권한 차단도 함께 확인한다.
7. 격리 복원 결과가 확인된 뒤 필요한 운영 스키마만 적용한다. 선택적 lookup 메타데이터 준비는 기존 보호 CLI와 별도 조건을 따르며, 신규 모집 개방이나 키 교체로 대체하지 않는다.

기존 참가자·입금·재고·당첨 기록을 변경하는 가짜 HTTP 요청이나 부하검사는 운영에서 실행하지 않는다. 복원 검증은 합성 DB 검사와 구분해 기록한다.

## 5. 기존 Netlify·Render에 맞춰 반영

1. 기존 서비스에 특정 커밋 또는 검증된 아티팩트를 배포할 수 있는지 관리 API에서 확인한다. Render의 main 추적이나 Netlify Stopped builds를 추정으로 변경하지 않는다. 서비스가 지원하는 방식을 확인하기 전 main 병합·Push로 배포를 유발하지 않는다.
2. 배포할 소스 SHA와 코드 지문을 고정하고 API와 React를 같은 소스로 빌드한다. 기존 Netlify API 연결과 Render SSE 경로·origin·쿠키 보안을 확인한다. 로컬 관리자 자동로그인, private-preview 인증 우회, 개발 DB 접속값을 배포물에 넣지 않는다.
3. 운영 백업·격리 복원과 필요한 스키마 확인 후 기존 API와 화면을 호환되는 조합으로 반영한다. 기존 키·업로드·기록을 보존하고, 문제 발생 시 사용할 양쪽의 이전 호환 배포 ID를 기록한다.
4. **최종 배포 상태는 테스트 모드 ON, `publicAdmissionOpen: false`여야 한다.** 이 문구는 배포 완료 판정 기준이며, 현재 운영 상태를 확인했다는 뜻이 아니다. 테스트 모드 OFF만으로 모집이 열리지 않도록 별도의 모집 개방 차단을 유지한다. 해당 보완 코드의 실제 검사 결과는 후속 검증 기록에 남긴다.
5. 테스트 초기화는 시험실 `laboratory-workspace` 기록에만 적용한다. 실제 참가자·입금·재고·당첨·문의·하트·채팅 기록과 전체 운영 초기화는 건드리지 않는다. 초기화 전 오래된 탭의 저장도 거부되어야 한다.
6. 테스트 모드를 OFF하더라도 일반 신청은 계속 차단되어야 한다. 사용자가 테스트를 마치고 실제 오픈을 별도로 확인하기 전에는 웹·오픈채팅 어느 쪽도 신규 신청을 받지 않는다. 오픈채팅 외부 게시·링크 활성화·참가 접수는 이번 배포 작업에 포함하지 않는다.
7. 실제 오픈 확인을 받더라도 개인정보 정책 지문·production release·행사 일정·모듈·권한 등 기존 보호조건을 그대로 확인한다. 전체 테스트 초기화나 정책 승인 하나만으로 실제 모집을 자동 개방하지 않는다.

| 일반 신청 차단 | 실제 공개 상태의 테스트 ON·모집 차단, 일반 화면 안내와 비활성 버튼. 운영에 가짜 신청을 저장하는 검사는 실행하지 않는다. |
| 관리자 시험실 | 같은 기존 사이트에서 로그인 후 합성 시나리오·저장·재열기·시험 데이터만 초기화 확인 |
| 기존 참가자 보호 | 의도하지 않은 초기화 없이 기존 본인 정보·고유번호·참가 상태·하트·대화 복구 확인. 개인정보 캡처는 공개하지 않는다. |

`/api/healthz`의 정상 응답은 프로세스 생존 확인이다. DB 스키마·운영 백업·실행 코드·모집 차단 검증을 대신하지 않는다. 배포 ID나 실행 SHA를 얻지 못하면 UNKNOWN으로 남기고 배포 성공이라고 보고하지 않는다. frontend/API 지문이 다르면 한쪽 성공으로 전체 앱 반영을 완료 처리하지 않는다.

## 7. 배포가 확인된 뒤 보스가 시험하는 순서

이 안내는 **최신 코드의 실제 배포 확인 후** 사용한다. 현재 운영 화면에 이미 아래 기능이 있다고 주장하지 않는다.

1. 평소 주소 `https://binpc2.netlify.app`를 연다. 일반 화면에는 테스트·점검 안내가 보이고 신청이 차단되어야 한다. 새 계정이나 실제 참가자 정보를 만들 필요가 없다.
2. 기존 관리자 로그인 방법으로 접속한다. PC방에서는 비밀번호 저장을 선택하지 않고, 완료 후 관리자 로그아웃과 사용한 창 닫기를 수행한다. 로그인 정보를 채팅이나 공개 캡처에 남기지 않는다.
3. **관리자 → 술번개 → 행사 설정·기록·관리 도구 → 선착순 시험실**로 들어간다. 관리자 테스트 모드 ON과 실제 운영 기록이 아닌 테스트 결과 표시를 확인한다.
4. 금요일 할로윈을 선택해 가상 3등 → 입금 신고 → 관리자 승인 → 프로필 일부 작성/완료 → 입장 → 카드·상품 결과를 차례로 누른다. 실제 송금이나 외부 발송은 하지 않는다.
5. 토요일 할로윈과 전국투어 금·토 1차를 각각 선택해 같은 흐름을 본다. 공유 정책에 따른 회비·복장 혜택·카드 수·상품 결과를 확인한다. 시험실의 합성 하트·대화는 실제 상대방 수신 검사가 아니다.
6. 시험실을 닫았다 다시 열어 같은 시험 기록이 이어지는지 확인한다. 관리자 시험실의 **테스트 데이터 초기화** 확인란과 버튼으로 시험 기록만 비운다. 다른 탭의 오래된 기록이 다시 저장되지 않는지도 확인한다. 기존 관리자 전체 운영 초기화 버튼을 사용하지 않는다.
7. 일반 창을 다시 열어 신청이 계속 차단되는지 확인한다. 테스트가 끝났다는 이유로 테스트 모드 OFF나 실제 모집 개방을 대신 실행하지 않는다. 수정할 부분을 정리한 뒤 사용자가 실제 오픈을 별도로 확인한다.

Galaxy·iPhone에서는 기존 본인 계정이 있을 때 프로필·고유번호·참가 상태·하트·대화를 먼저 확인한 뒤 잠금/해제, 은행·카카오톡 이동 후 복귀, 새로고침, 같은 브라우저 재열기, 네트워크 끊김/복구 순서로 비교한다. 시험실의 합성 프로필만 확인한 것을 실제 참가자 복구 완료로 바꾸지 않는다. 진짜 17시 만료된 현장 프로필은 무단 복원하지 않으며 별도 신청·입금·당첨 이력은 보존한다. 실물 기기 결과를 얻기 전 해당 항목은 UNKNOWN이다.

## 8. 문제가 생기면

- 신규 신청 차단과 테스트 모드를 유지한다. 모듈 OFF는 기존 기록 삭제가 아니다.
- 양쪽 배포 ID와 오류 단계·시각·코드 지문을 남기고 이전 호환 코드로 되돌릴 방법을 검토한다. 운영 DB를 과거 덤프로 무조건 덮거나 새 데이터가 생긴 뒤 일괄 복원하지 않는다.
- 키 교체·브라우저 저장소 전체 삭제·운영 17시 초기화·실제 재고 초기화를 복구 방법으로 사용하지 않는다.
- 접속이 막히면 현재 실행 환경, 실패 호스트, proxy CONNECT/원격 HTTP/인증/배포 단계 중 어디에서 실패했는지 나눠 보고한다. 이미 완료한 코드 저장·검사·준비 작업과 미실행 백업·복원·배포를 구분한다.
- 필요한 조치는 기존 보안 연결 복구와 확인되지 않은 백업·복원 증거 확보에 한정한다. 이미 받은 운영 배포 승인을 다시 요청하거나 새 유료 시험사이트 생성을 요구하지 않는다.
