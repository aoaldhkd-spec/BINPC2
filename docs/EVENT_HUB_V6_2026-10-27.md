## 저장·보호 설계

- PostgreSQL의 별도 원장과 유일 인덱스가 행사별 소유자·순번 중복을 막는다. 프로세스 메모리를 정본으로 사용하지 않는다.
- 쓰기는 트랜잭션과 기존 reset advisory lock → hub lock 순서로 직렬화한다. 100명/2개 서비스 인스턴스와 실제 HTTP 100개 쿠키 세션을 별도로 검사했다.
- 애플리케이션 전체 필드를 무조건 받지 않는다. 고객·관리자 동작을 분리하고 관리자 HMAC 토큰은 기존 검증기를 재사용한다. 오류 로그는 요청번호·단계·오류코드만 기록한다.
- 원장 내용은 AES-256-GCM, 레코드 종류/ID를 AAD로 인증한다. 기존 SESSION_SECRET에서 HKDF로 전용 키를 유도하며, 서버에는 원문 비밀번호/복구코드를 저장하지 않는다. 라우팅/유일성에 필요한 제한된 식별자·순번 메타데이터만 암호문 밖에 둔다.
- SESSION_SECRET은 이번에 변경하지 않았다. 향후 키 변경·폐기 시 원장 암호화 키의 보관/재암호화 계획이 필요하다. 키가 없거나 인증 복호화에 실패하면 데이터를 비우거나 새 원장으로 덮어쓰지 않고 실패한다.
- 행사 시작 전 프로필 초안은 기존 공개 프로필·채팅·하트 목록에 넣지 않는다. 현장 프로필의 신청 소유자 ID·신청번호·PIN은 타 참가자용 응답/SSE에서 제거한다.
- 기존 23시/24시/01시/17시 스케줄러와 하트·채팅 구현은 교체하지 않았다. 자정 이후 관리자가 시작한 주기도 이전 저녁 행사 날짜와 연결한다.

## 재현 가능한 격리 개발 준비

기존 체크아웃과 잠금파일을 사용한다. 새 worktree는 만들 필요가 없다. 이 클라우드에서는 `/workspace/.binpc2/tool-env.sh`로 Corepack/XDG 쓰기 위치를 초기화했다. Node 24.19.0, 저장소 고정 pnpm 11.21.0, PostgreSQL 16, 시스템 Chromium으로 검증했다. 워크플로의 Node 22/GitHub 호스트 조합 자체는 아직 실행하지 않았다.

1. localhost의 개발 PostgreSQL을 사용하고, 각각 `DATABASE_URL=.../binpc2_hub_dev?sslmode=disable`, `HUB_TEST_DATABASE_URL=.../binpc2_hub_test?sslmode=disable`, `TEST_DATABASE_URL=.../binpc2_reset_test?sslmode=disable`로 분리한다. 운영 URL을 넣지 않는다.
2. `NODE_ENV=development node scripts/prepare-event-hub-e2e.mjs database`. 이 스크립트는 세 고정 DB 이름과 loopback 호스트만 허용하며 새 원장에 additive migration을 적용한다. 현장/운영 데이터 삭제 명령은 없다.
3. `pnpm install --frozen-lockfile && pnpm run build`.
4. 로컬 API에 SESSION_SECRET을 안전하게 주입하고 `PORT=8081 node artifacts/api-server/dist/index.mjs`를 실행한다. 키를 출력/커밋하지 않는다. `PORT=3001 LOCAL_API=1 API_PROXY_TARGET=http://127.0.0.1:8081 pnpm dev`로 프런트엔드를 실행한다. Vite 기본 운영 API 프록시를 사용하지 않는다.
5. 준비된 **전용 로컬** API/DB에 한해 `HUB_E2E_BASE_URL=http://127.0.0.1:3001 node scripts/prepare-event-hub-e2e.mjs activate`. 이 동작은 로컬 fixture의 module ON과 회식 시작만 설정한다. 실제 공개 행사를 만들지 않는다. 테스트 인증을 화면에 출력하지 않고 `.local/event-hub/browser.env` 또는 CI 환경 파일에 저장한다.
6. 생성한 로컬 binding을 주입한 뒤 위 검증을 실행한다. 테스트가 만드는 접수/은행 승인/문의/재고는 모두 가상 데이터이며 실제 송금/외부 발송과 다르다.
7. 사용자 화면 `/events`, 기존 관리자 화면의 `술번개` 탭, 기능 ON/OFF는 `설정 → DB헬스 → 기능 붙이기/떼기`에서 검토한다. 새로운 운영 DB 마이그레이션·모집 시작·기존 회식 시작은 각각 별도 작업이다.

로컬 검토용 그림은 `.local/event-hub/evidence/`에도 보존했다: `waiting-mobile.png`, `waiting-desktop.png`, `save-failure.png`, `admin-rank-3-mobile.png`, `admin-rank-4-mobile.png`, `admin-rank-4-desktop.png`. 개인정보/복구코드를 담은 실행환경 파일은 커밋하지 않는다.

## 미완료·다음 개발 지점

1. **자동 파기/법적 고지:** 실제 운영 주체의 고지 원문, 운영기록·금융 증빙·분쟁·재사용 정보·백업별 보관기간/예외·삭제 승인 범위를 확정한 뒤 별도 retention 작업과 실제 운영 마이그레이션을 검토한다. 현재 검토 예정일만 기록하며 운영 자동 삭제를 실행하지 않는다.
2. **시험실:** 현재 순위/회비/상태/역할/카드 한도 UI를 완전한 신청·대기방·관리자 상담 모의 어댑터로 확장할 수 있다. `EventLaboratory.tsx` 제거 시에도 공유 quote/프로필 판정과 서버/브라우저 자동 테스트는 남는다.
3. **미디어:** 검증된 HTTPS 링크/미리보기 경로를 실제 운영 자료로 확인해야 한다. 파일 업로드·파일 매직/바이러스 검사 파이프라인은 구현하지 않았다. 업로드가 필요하면 별도 작업으로 연결한다.
4. **알림:** 행사 안내 설정/별도 마케팅 수신 동의는 저장한다. 실제 광고/관리자 Push 발송기, 수신거부 링크, 기기별 백그라운드 동작과 외부 발송은 승인·별도 검증이 필요하다. 기존 참가자 하트/1:1 Push 정책은 바꾸지 않았다.
5. **전체 운영 UI:** 다단계 생성 마법사 대신 순서 있는 편집 폼/미리보기/초안을 제공한다. 표의 대량 처리·전용 회원 복구/잠금 해제 UI·모든 운영 이력의 사용자용 타임라인·모든 저장 상태 스크린샷은 추가 보완 대상이다.
6. **운영 전 검증:** 새 DB의 additive migration, 기존 SESSION_SECRET 보존/재암호화 계획, 운영 도메인의 쿠키 프록시·SSE·미디어·실기기·실제 상품 수량/배송을 승인 범위 내에서 확인한다. 운영 수집/공개·금전·실제 발송·Secret 변경·파괴적 작업을 이번 코드 개발 완료와 혼동하지 않는다.

## 영향과 되돌리기

- 새 event_hub 플래그는 기본 OFF다. 운영 중 OFF로 내려도 신청·입금·문의·상품 원장은 삭제하지 않는다. 기존 참가자 현장 기능은 유지한다.
- 변경을 되돌릴 때 신규 원장 삭제/다운 마이그레이션을 실행하지 않는다. 별도 기능을 OFF하고 이 개발 커밋을 되돌리는 방식으로 검토한다. 이미 신규 행사 기능으로 운영했다면 먼저 신청·입금 기록 보존/복구 계획이 필요하다.
- 운영 배포·push·실제 공개·실제 외부 메시지/금융·운영 DB 변경/삭제는 **미실행**이다.
