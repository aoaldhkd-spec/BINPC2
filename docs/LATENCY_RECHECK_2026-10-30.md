# 실제 화면 전환·저장 속도 재검사

사용자는 2026-10-30 화면 전환과 저장을 밀리초 단위로 다시 검사하고 개선하도록 요청했다. 기능이 작동한다는 사실과 빠르게 작동한다는 결과를 구분한다.

## 현재 기준

기존 사이트에는 `1b37c23ac91d3f545eb751471826dc56c658ee2d`가 실제 반영됐다. Netlify `6ae416ba55bc0a11da7b9b51`, Render `dep-dbi1c7tg1s2s73dmmv80`, CI [40999323606](https://github.com/aoaldhkd-spec/BINPC2/actions/runs/40999323606) 27단계 성공, 배포 후 실제 접속 검사 8개 통과다. 이 문서의 후속 속도 수정은 아직 커밋·최종 CI·재배포·실사이트 재측정 전이다.

보스 잠금 ON·시험실 ON·일반 신청 차단을 유지한다. 실제 신청·입금·입장·초기화는 운영 검증에서 실행하지 않았다. 기존 3,274행·102개 이미지·기존 이벤트 장부 30행의 내용과 대화방 생성시각이 보존됐다. 대화방 4행의 메타데이터만 바뀌었고 접속 검증 과정의 빈 owner 세션 2개가 추가됐다. [실제 반영 근거](latency-recheck-20261030/previous-live-release.json).

## 실제 사이트의 수정 전 측정

[원본 측정 요약](latency-recheck-20261030/before-live-read.json)은 기존 인증 세션을 재사용한 읽기 전용 검사다. 새 신청·저장·세션 생성 없이 수행했다.

| 첫 신규 세션의 신청 화면 | 4,958ms, 2초 목표 미달 |
| 기존 세션의 홈→신청 실제 데이터 표시 | 2,385 / 1,860 / 1,882ms |
| 상태 API 전체 응답 | 1,537 / 1,492 / 1,512ms |

처음 두 배포 후 확인은 기본 5초의 표시 대기시간을 넘겼고 실패 기록을 보존했다. 기능 검사의 외부 자산 대기는 별도로 20초까지 관찰했으며, **속도 목표 2초는 그대로 유지해 4,958ms를 실패로 기록**했다. 제목만 먼저 표시하는 것을 실제 사용 가능 상태로 세지 않는다.

Render의 지역은 Oregon이고 현재 DB pooler 연결 주소는 `ap-northeast-2`를 가리킨다. Supabase 프로젝트 자체 지역 메타데이터는 권한 403으로 확인되지 않았으므로 UNKNOWN이다. DB 읽기 인증은 정상이며 전체 연결 실패로 표현하지 않는다. 서버·DB 사이의 반복 왕복이 지연에 영향을 준다는 근거가 있지만, 실제 네트워크 구간을 따로 계측한 결과는 아니다. 서비스 위치·요금제·연결 설정은 변경하지 않았다.

## 후속 코드 변경

- 상태 읽기의 잠금·키 확인은 유지하면서 같은 트랜잭션의 필요한 조회를 묶는다. 개인별 후보와 전체 조회 캐시를 섞지 않는다.
- 저장 사전 조회에서 고정 설정·앱 설정·필요한 본인 신청 목록을 한 번에 읽는다. 기존 승인·닉네임·재고·중복 검사를 유지한다.
- 세션 및 일반 저장 응답에 검증된 최신 상태를 선택적으로 함께 받아 후속 HTTP 왕복을 줄인다. 기존 서버·불완전한 응답·읽기 실패는 기존 재조회로 확인한다.
- 관리자/참가자 범위, 요청 ID, 세션 변경, 역순 응답을 검사한다. 요청 중 도착한 새 승인·문의 알림은 무시하지 않는다.
- 정적 신청 코드만 미리 받는다. 개인 API 선조회나 권한 없는 데이터 캐시는 추가하지 않는다.
- 로딩 반응, 실제 버튼이 활성화되는 시점, 서버 저장 확정, 다음 단계 표시를 각각 측정한다. 저장 완료를 미리 표시하지 않는다.

### DB 지연 모델 비교

[전체 원본 수치](latency-recheck-20261030/comparison-v2.json). 같은 비교 시나리오의 총 HTTP 요청은 **68→48회**, 예상 밖 실패0건이다. 아래 값은 **5표본 중앙값**이며 P95가 아니다.

| 작업 완료 기준 | A 중앙값 | B 중앙값 | 변화 |
|---|---:|---:|---:|
| 미인증 상태 조회 | 856ms | 494ms | 약42% 감소, SQL7→4회 |
| 기본정보 초안 저장 | 1,225ms | 993ms | 약19% 감소, SQL9→7회 |
| 본인 상태 조회 | 1,221ms | 739ms | 약39% 감소, SQL9→5회 |
| 공지 동의 저장 **+ 서버 최신 상태 확인** | 2,689ms | 1,844ms | 약31% 감소, HTTP2→1회 |
| 입금 신고 **+ 서버 최신 상태 확인** | 2,564ms | 1,721ms | 약33% 감소, HTTP2→1회 |
| 같은 입금 신고 재시도 **+ 최신 상태 확인** | 2,077ms | 1,347ms | 약35% 감소, HTTP2→1회 |

새 응답이 상태까지 포함하므로 일부 **단일 POST 응답**은 더 오래 걸린다. 예를 들어 동의 POST만 비교하면1,468→1,844ms, 입금 신고 POST는1,344→1,721ms다. 비교 기준은 필요한 최신 상태까지 확보하는 전체 흐름이며 단일 API가 모두 빨라졌다고 하지 않는다. 중복 신고 재시도는 기존 결과를 재사용하고 두 번 저장하지 않는다.

**2초 목표는 PARTIAL이다.** 입금 신고+상태 확인5회 중 최대가 **2,686.7ms(약2,687ms)**로 목표를 넘었다. 중앙값이 빨라졌다는 이유로 이 실패를 제외하지 않는다. 추가 대기 원인은 아직 분리되지 않았으며, 표본5개의 최대값을 운영 P95로 해석할 수 없다. 인증·잠금·재고·공지 동의·중복 방지 검사는 유지했다.

API 린트 첫 실행은 기존 검사 파일의 `prefer-const` 1건으로 멈췄다. 해당 선언만 `let`→`const`로 고친 뒤 전체 린트와 관련 DB 사례 1개를 재검사해 통과했고 최초 실패 기록도 보존한다. A의 UI963/API613을 최신 B의 검사 개수로 쓰지 않는다.

후속 확인은 B 최종 검사→개발 브랜치 저장·CI→승인된 기존 서비스 반영→실제 실행 버전·보스 잠금·기록 보존→기존 세션의 읽기 전용 지연 비교 순서다. 운영 저장을 측정한다는 이유로 가짜 입금·신청을 만들거나 사용자 시험 기록을 초기화하지 않는다. 운영 쓰기 성능은 별도 허용된 시험 흐름에서만 확인한다.

기존 보스 전용 주소는 계속 사용할 수 있지만, **B가 반영되어 더 빨라졌다는 확인은 아직 없다.** 실물 기기와 실제 통신망의 최악 지연, 수시간 장시간 성능은 UNKNOWN이다. 현재까지 확인한 A 기록과 B 측정·실패를 모두 보존한다.
