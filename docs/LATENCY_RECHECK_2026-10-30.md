## 후속 코드 변경

- 상태 읽기의 잠금·키 확인은 유지하면서 같은 트랜잭션의 필요한 조회를 묶는다. 개인별 후보와 전체 조회 캐시를 섞지 않는다.
- 저장 사전 조회에서 고정 설정·앱 설정·필요한 본인 신청 목록을 한 번에 읽는다. 기존 승인·닉네임·재고·중복 검사를 유지한다.
- 세션 및 일반 저장 응답에 검증된 최신 상태를 선택적으로 함께 받아 후속 HTTP 왕복을 줄인다. 기존 서버·불완전한 응답·읽기 실패는 기존 재조회로 확인한다.
- 관리자/참가자 범위, 요청 ID, 세션 변경, 역순 응답을 검사한다. 요청 중 도착한 새 승인·문의 알림은 무시하지 않는다.
- 정적 신청 코드만 미리 받는다. 개인 API 선조회나 권한 없는 데이터 캐시는 추가하지 않는다.
- 로딩 반응, 실제 버튼이 활성화되는 시점, 서버 저장 확정, 다음 단계 표시를 각각 측정한다. 저장 완료를 미리 표시하지 않는다.

### DB 지연 모델 비교

[전체 원본 수치](latency-recheck-20261030/comparison-v2.json). 같은 비교 시나리오의 총 HTTP 요청은 **68→48회**, 예상 밖 실패0건이다. 아래 값은 **5표본 중앙값**이며 P95가 아니다.

| 작업 완료 기준 | A 중앙값 | B 중앙값 | 변화 |
|---|---:|---:|---:|
| 미인증 상태 조회 | 856ms | 494ms | 약42% 감소, SQL7→4회 |
| 기본정보 초안 저장 | 1,225ms | 993ms | 약19% 감소, SQL9→7회 |
| 본인 상태 조회 | 1,221ms | 739ms | 약39% 감소, SQL9→5회 |
| 공지 동의 저장 **+ 서버 최신 상태 확인** | 2,689ms | 1,844ms | 약31% 감소, HTTP2→1회 |
| 입금 신고 **+ 서버 최신 상태 확인** | 2,564ms | 1,721ms | 약33% 감소, HTTP2→1회 |
| 같은 입금 신고 재시도 **+ 최신 상태 확인** | 2,077ms | 1,347ms | 약35% 감소, HTTP2→1회 |

새 응답이 상태까지 포함하므로 일부 **단일 POST 응답**은 더 오래 걸린다. 예를 들어 동의 POST만 비교하면1,468→1,844ms, 입금 신고 POST는1,344→1,721ms다. 비교 기준은 필요한 최신 상태까지 확보하는 전체 흐름이며 단일 API가 모두 빨라졌다고 하지 않는다. 중복 신고 재시도는 기존 결과를 재사용하고 두 번 저장하지 않는다.

**2초 목표는 PARTIAL이다.** 입금 신고+상태 확인5회 중 최대가 **2,686.7ms(약2,687ms)**로 목표를 넘었다. 중앙값이 빨라졌다는 이유로 이 실패를 제외하지 않는다. 추가 대기 원인은 아직 분리되지 않았으며, 표본5개의 최대값을 운영 P95로 해석할 수 없다. 인증·잠금·재고·공지 동의·중복 방지 검사는 유지했다.
