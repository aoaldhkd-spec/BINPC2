# 개인정보 삭제이력과 백업 복원 확인

기존 앱 자료 백업과 별개로, 최신 운영 DB의 암호화된 `privacy-erasure` 기록을 읽어 독립된 암호화 체크포인트를 만드는 경로를 준비했다. 키를 새로 만들거나 변경하지 않는다. 운영 데이터 삭제·자동 파기는 실행하지 않는다.

## 확인 순서

1. 이미 검증한 앱 자료 백업을 지정하고, 운영의 삭제이력만 읽기 전용으로 조회한다.
2. 체크포인트를 기존 복구키로 암호화한다. 키·운영 환경값·평문 개인정보는 체크포인트 파일에 넣지 않는다.
3. 기존 비공개 Google Drive 백업 폴더에 **앱 백업과 다른 파일**로 업로드한다. 다시 내려받은 파일의 크기와 SHA-256을 비교한다.
4. 격리 복원 DB에서 제품의 `assertPrivacyRestoreCheckpoint`를 실제 호출한다. 이 조회는 `BEGIN READ ONLY`로 실행하며, 운영 DB 연결을 거부한다.
5. 최신 체크포인트의 삭제이력이 복원 DB에 없거나 삭제된 자료가 다시 나타나면 실패한다. 이때 운영 공개·기존 자료 덮어쓰기·자동 삭제로 해결하지 않는다.

백업 내부의 오래된 삭제이력을 꺼내 그 백업 자체를 인증하지 않는다. 체크포인트는 운영에서 별도로 읽은 시각·용도·관련 백업 SHA를 포함하며, 현재 작업의 확인 도구는 조회 후 30분 이내 사본만 받는다. 과거 재해 복구에서 최신 상태를 증명할 수 없다면 격리 복원 결과를 보관하고 공개를 차단한 채 별도 검토해야 한다.

## 준비한 도구

비공개 작업 폴더 `.local/current-protected-backup/`의 파일:

- `prepare-erasure-checkpoint.py`: 기존 운영 연결을 읽기 전용으로 확인하고 별도 암호화 사본과 업로드 실행기를 준비한다.
- 체크포인트 폴더의 `drive-checkpoint.py`: 기존 비공개 폴더 업로드·재다운로드·해시 확인. 별도 명시 실행이 필요하다.
- `verify-privacy-checkpoint.cjs`: 기존에 검증해 둔 격리 복원 DB를 다시 읽고 최신 외부 체크포인트를 대조한다.
- `restore-v3-with-privacy.cjs`: 기존 전체 복원 절차 뒤 위 대조를 필수로 호출한다. 원래 복원 실행기와 결과는 보존한다.

제품 API·배포 번들·운영 설정은 이 도구 준비 과정에서 수정하지 않았다. 도구 자체의 가짜 입력 검사 7개는 통과했다: 독립 사본 확인, 오래된 사본 거부, 자기 백업으로 인증 거부, 해시 불일치 거부, 삭제자료 재등장 거부, 최신 삭제이력 누락 거부, 로컬 Docker 주소 경계 확인. 이는 실제 운영 조회·Drive 업로드 성공을 대신하지 않는다. 실제 실행 결과는 별도 보호된 증거로 확인해야 한다.

Docker에서 서버 주소가 bridge IP로 보이는 경우에도 임의 사설 주소를 허용하지 않는다. 실제 클라이언트의 localhost 접속·격리 DB 이름과 현재 `binpc2-dev-postgres`의 실행 상태·정확한 localhost 포트 매핑·서버 주소가 모두 일치해야 한다. 다른 컨테이너나 알 수 없는 주소는 차단한다.

최초 대조는 PostgreSQL이 주소를 CIDR 표기(`/32`)로 반환하여 안전 경계에서 차단됐다. `host(inet_server_addr())`로 호스트 주소를 읽도록 바로잡고 재검사했다. 컨테이너·포트·localhost 제한은 유지했으며 운영 쓰기는 없었다. 0건의 의미와 아래 범위 제한은 그대로 남는다.

## V2: 기존 현장 자료의 재등장 차단 경로

V1 검증 결과는 그대로 보존한다. V2는 앱 백업에 실제 존재하는 알려진 개인정보 KV 테이블만 골라, 최신 운영의 행 ID와 내용 SHA-256을 별도 암호화 체크포인트에 포함한다. 프로필·하트·대화·기기 연결·푸시 구독 등 해당 범위의 본문을 로그나 체크포인트에 복제하지 않는다. 행사 주기·초기화 표시는 허용된 필드만 읽는다.

복원본에 현재 운영에 없는 행이 있거나, 같은 ID의 내용이 달라졌거나, 행사 주기·초기화 표시가 달라졌으면 복원 공개 확인을 실패시킨다. 정상 수정과 개인정보 삭제·축약을 해시만으로 구분하지 않으므로, 정상 수정도 차이가 있으면 검토가 필요하다. 자동으로 행을 지우거나 운영을 덮어쓰지 않는다. 최신 운영에만 추가된 행 수는 별도로 표시하며, 해당 백업 시점 이후의 자료까지 복원했다고 주장하지 않는다.

실행기는 `prepare-erasure-checkpoint-v2.py`, 체크포인트 폴더의 `drive-checkpoint-v2.py`, `verify-privacy-checkpoint-v2.cjs`, `restore-v3-with-privacy-v2.cjs`이다. 합성 보호검사 12개를 통과했으며, 여기에는 삭제행 재등장·같은 ID의 개인정보 축약·17시 초기화/주기 변경·알 수 없는 테이블/불필요한 평문 포함 차단이 포함된다. V2의 실제 운영 읽기·외부 업로드·복원 대조 결과는 별도 실행 증거로 확인해야 한다.

**V2 실제 대조 PASS:** 2026-10-30 06:59:06 UTC 앱 백업과 별도로07:01:54 UTC 최신 운영 체크포인트를 읽었다. 비공개 Drive 업로드·재다운로드 후07:07:14 UTC 실제 격리 복원 DB에서 제품 검사와 현장 해시 검사를 실행했다. 삭제ledger0건, 현장9테이블3,273행과 초기화 상태가 일치했다. 체크포인트 SHA256은 `52cdc94874d4f4a7adb38b7c996d54a4c44b7420ca725bd876205eff3004393a`, 관련 앱 백업 SHA256은 `c5b12df6c779d04f9b5cce6e6d8160877a42d47fd9cf72e45dc9e5bf03b9d4ac`다. 운영 쓰기·키 변경·자료 삭제는 없었다.

## 확인 범위와 한계

- 체크포인트 대상은 새 개인정보 처리 경로가 기록한 행사 신청·회원·문의 등의 삭제·최소화 이력이다.
- 삭제이력 수가 0이면 **그 조회 시점에 기록된 삭제이력이 없다는 뜻**이다. 과거 전체 삭제나 미래 삭제까지 보장하지 않는다.
- 기능 도입 전 삭제의 완전한 이력과 Supabase 전체 플랫폼 복원은 별도 범위다. V2의 현장 KV 대조는 지정 백업에 들어 있는 알려진 테이블과 조회 시점만 대상으로 하며, 테이블 목록 밖이나 미래의 변경은 보장하지 않는다.
- 체크포인트의 외부 최신화 주기·장기 보관기간은 이번 도구가 임의로 확정하지 않는다. 새 삭제가 생기면 그 이력을 포함하는 최신 독립 체크포인트가 필요하다.
- 기존 앱 자료 암호화 파일, 별도 복구키, 별도 최신 삭제이력 사본을 각각 확보해야 한다. 이 문서는 실제 외부 보관이나 복원 통과 증거가 아니다.
