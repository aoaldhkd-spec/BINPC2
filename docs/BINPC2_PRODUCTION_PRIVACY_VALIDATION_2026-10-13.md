상태: CURRENT 작업 브랜치 검토 자료 / 운영 배포 승인·개인정보 처리방침 확정 아님.
원본 기준: PR #9 (main은 99393b47); 운영 데이터 수집/파기/Secret 변경을 시행하지 않는다.

## 1. 코드에서 확인된 개인정보·보관 경계
- 자동 행사초기화 대상(KV): `profiles`, `likes`, `anonymous_reports`, `chats`, `messages`, `contact_shares`, `contact_share_events`, `notifications`, `signal_sends`, `group_chats`, `group_participants`, `group_messages`, `group_opt_outs`, `chat_reads`, `blocked_users`, `profile_views`, `user_signals` (`db-admin-wipe-plan.ts`).
- 유지 대상: `event_anonymous_archives`, `event_sales_reports` (원문 신원 대신 합계 저장; 실제 재식별 가능성·보관기간은 별도 평가).
- 일반 초기화 대상에 없음: `device_secrets`, `push_subscriptions`, `session_history`, `app_image_store`, `app_settings`의 일부 자격 관련 항목, 별도 PostgreSQL `app_image_store` 원본, 서버/배포 로그, 외부 백업. **미포함은 실제 전체 삭제 보장을 부정한다.**
- `app_image_store` 별도 SQL 존재; `device_secrets`는 기기 세션 인증 해시, `push_subscriptions`는 푸시 관련 식별자료로 취급하고 보안·개인정보 검토 필요.
- `event_anonymous_archives`는 행사 시작·종료·메시지/하트 합계 중심이지만 작은 집단에서는 다른 현장 정보와 결합해 추정 가능할 수 있으므로 공개 범위와 보관기간 확정 전에는 관리자 외 제공 금지.

## 2. 법적 검토 대상 — 숫자 임의 확정 금지
- 개인정보 처리목적별 필수 항목과 목적 달성 시점, 행사 참여자 사진/연락처/프로필, 연락처 교환 이력, 기기 인증정보, 푸시 구독정보, 회원 복구용 PIN, 관리자 이력, 접속·보안 로그, 외부 백업 별로 구분한다.
- 수집·이용, 제3자 제공, 보관기간, 파기 절차/방법, 처리 위탁·국외 이전 여부, 문의처, 열람·정정·삭제·동의 철회 경로, 사고 대응을 운영자가 확정해야 한다.
- 법적 근거: 대한민국 개인정보 보호법 제21조(시행 2026-09-11), 국가법령정보센터 https://www.law.go.kr/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=1020398651 . 보유기간 경과/목적 달성 시 지체 없이 파기, 복구 불가능한 처리, 다른 법령상 보존분 별도 분리 저장 관리.
- 현재 **보관기간 숫자 UNKNOWN**. 계약·법적 근거 없는 '17시에 개인정보 완전 삭제' 문구와 실제 DB 파괴 자동화 추가 금지.
- 개인정보 법률 자문/실제 운영자 승인 완료까지 처리방침을 '확정/준수 완료'로 표시하지 않는다.

## 3. 150명 부하 — 검증과 배포 경계
- 150명 각각 고유 프로필/기기, 모바일 SSE 연결, 하트, 1:1 메시지/채팅방, 단체채팅, 관리자 설정 변경, 재연결, 01시 마감과 17시 초기화 인접 시점을 **별도 가짜 DB/임시 PostgreSQL**에서 검증.
- 동시 150 접속/재연결에서 인증 성공률, 지연시간 p50/p95/p99, HTTP 429/5xx, DB 커넥션/CPU/메모리, 이벤트 중복/누락, fanout 개인정보 노출, 클라이언트 수신부터 화면 반영까지 시간 기록.
- 실제 Render 인스턴스 규격·DB 연결상한·Netlify 빌드·모바일 네트워크가 다르므로 합성 PASS를 현장 보증으로 승격하지 않는다.
- 서버 장애 시 부하 중지, 비용/속도 상한, 테스트 자료 자동 정리와 백업 확인 필요. 운영 데이터에 150개 가짜 참가자를 생성하지 않는다.
- 성능 임계값은 운영자와 실제 용량 근거를 확인해 결정. 수치를 발명하지 않는다.

## 4. NPC 하트 다중 서버 동시 전송
- 정상 정책: 행사 시작·종료 각 1회 충전, 일반 ❤️💙💗💚 각 1회 + 무지개 4회. 기존 하트 기록·수신자별 중복은 유지.
- `db-npc-heart-recharge.ts`의 현재 잔량 산술/테스트는 구현. **두 서버가 같은 하트 잔량을 동시에 검사하고 서로 다른 수신자에게 보내는 상황에서 DB 원자적 선점 또는 직렬화 검증은 별도 확인**; 테스트 통과만으로 전역 한도 보장이라고 하지 않는다.
- 별도 격리 DB 동시성 테스트: 같은 NPC/행사/종류에서 동시에 두 수신자에게 INSERT, 최종 수량 1회 이하, 무지개 5개 동시 시도 시 최대 4회, 중복 대상/색/출처 보장, DB 장애 시 원장/차감 불일치 없음. multi-instance advisory lock 범위 확인 후 최소 수정.
