# BINPC2 V6 — 최종 개발 보완·내부 검사·기존 사이트 반영 준비

별도 시험사이트·유료 서비스·새 DB 서비스·터널·독립 HTML은 만들지 않았다. 시작 원격 `530279a4c712711f61adff8a160360e65b5e4df5`에서 같은 `feat/event-hub-v6-20261027`을 이어갔다. main/운영 배포/실제 모집/외부 발송/운영 개인정보 변경·삭제는 실행하지 않았다.

## 1. 남은 순수 개발과 실제 완료 범위

요청한 **A 관리자 실제 검사자료 연결, B 새 로고 원본 관리, C 실제 PostgreSQL 100/150명 혼합·재시작 시험**을 구현했다. 기존 기능을 재제작하지 않았다. 기능별 [A/B/C/D 대조표](EVENT_HUB_V6_INTEGRATED_CHECKLIST_2026-10-27.md)에서 이전 C 세 항목의 근거를 갱신했다.

**V6 전체/운영 가능을 완료 처리하지 않는다.** 2초 성능 목표는 일부 측정에서 초과했고, 전체 기기의100ms 화면 응답·몇 시간 실사용·실물 휴대폰·운영 배포 버전 확인은 남는다. 기능 검사 성공과 이런 미확정 항목을 구분한다. 순수 기능 구현의 새 누락은 이번 대조에서 발견하지 않았으며, 남은 기술 확인은 성능 범위 확대와 실제 운영환경/휴대폰 검증이다.

## 3. C — 실제 혼합·지속 검사와 이전503

환경: Node24·PostgreSQL16, 컴파일된 Express와 실제 HTTP, 정상 PG 세션/관리자 로그인/요청 제한. 엄격한 loopback 시험 DB `binpc2_hub_load_v6`만 허용한다. 운영 API·SSE·DB·계정/키는 주입하지 않았다. 행사 시각만 명시적 격리 fixture로 이동하고 **지속시간/CPU/지연은 실제 벽시계**로 측정했다.

100명 동시 신규 신청 후150명의 신청/동의/입금신고/부분·완성 프로필/수동 승인/문의/입장/3장 뽑기/중복 지급을 섞었다. 지속 구간은150세션이 약15초마다 묶음 요청(일부 문의 쓰기/관리자 답장)을 하는 방식이다. **150RPS 상시 부하나150개 휴대폰/브라우저를 실행한 결과는 아니다.** 실제 HTTP/API 프로세스 재시작 후 복구했다. 저장 완료 응답 본문을 고의로 버린 뒤 같은 requestId를 재시도했고, 별도 PG 검사는 COMMIT 응답 유실도 재현한다.

|---|---|---|

최종 지속 검사:150명 동일PIN/닉네임/신청/승인/카드 재시작 복구 확인, 정상 지속 구간 P95 **1204.5ms**, 최대1364.1ms. 프로세스 RSS 170.04→289.19MiB(최대299.54), heap 50.85→20.46MiB, CPU 평균3.89%/최대52.77%. 마지막5분 RSS범위[289.06, 295.26]MiB. DB연결 최대12/종료직전12, 동시잠금대기 최대10,1초 표본 중 최대 transaction 0.277초. API/관측기 종료 후 같은 DB연결은 **0**.

RSS는 warm-up 후 예약 메모리가 늘었고 마지막5분 범위와 heap 감소를 함께 기록했다. 이것만으로24시간 누수 부재를 보장하지 않는다.15분 반복을5시간 장기 성적으로 바꾸지 않는다.7건/8건409는 고의 중복 경품 지급 거절이며 예상 상태를 검사했다. 초기 fixture/입장revision 실패는 별도 보존하고 이 성공 실행에 섞어 숨기지 않았다.


원인과 수정:

- 과거 누적5044 소유자의100세션 요청에서 **48성공/52×503**, 약8초로 재현했다. 진단 로그의 `POOL_CONNECTION_TIMEOUT`을 확인했다. 전체 소유자 복호화가 연결과 이벤트루프를 오래 점유하는 경로였으며 보안/요청 제한을 없애서 통과시키지 않았다.
- 기존 복구 해시 인덱스로 본인만 찾고 암호화 payload의 소유권을 다시 검증한다. 참가자 문의도 본인 thread만 읽는다. 신청 닉네임 중복 검사는 HMAC 조회 메타데이터와 기존 행 호환 경로를 사용하며 중복 규칙·잠금은 유지한다.
- 누적601개 기존 신청의 **조회 메타데이터만** 격리 준비했다. 암호문·키·revision·업무시간/updated_at 불변과 옛 평문 회원의 중복 방지를 PG에서 검증했다. 운영에서는 자동 실행하지 않는다.
- 실제 혼합 시험이 발견한 중복 `application.enter`의 revision/이력 이중 갱신을 고쳤다. 같은 요청의 재시도도 인증/현재cycle/현장 프로필 검사를 다시 하지만 revision을 또 올리지는 않는다. 이어지는 카드 요청409와 진짜17시 차단을 함께 검사했다.
- 동일 누적DB·키·기록을 유지한 여러 재검사에서503 미재발을 확인했다. 새 깨끗한 DB1회의 성공으로 바꿔 말하지 않는다. 연결 수/잠금은 실제 표본이고 1초 사이의 모든 순간을 관측한 것은 아니다.

속도: 동일 환경 초기100명 신청 P95가 **5292.8→2094ms**로 개선됐다. 2초 임시목표보다94ms 높다. 승인→참가자 화면 **1601/2229ms**, 답장→참가자 화면 **1328/1346ms**(각 실행1회). 이 값은 화면에 실제 표시된 시점이며 전기기의 P95를 뜻하지 않는다. 실제 모바일100ms/2초 성능을 보장하지 않는다.
