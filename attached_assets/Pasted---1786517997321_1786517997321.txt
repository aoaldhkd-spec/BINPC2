하트시그널 웹 시제품 최종 전수조사 및 안정화 작업

이번 작업의 목적은 새로운 기능을 개발하는 것이 아니라,



현재 구현된 모든 기능을 전수조사하고, 불필요한 코드와 쓰레기 코드를 정리하며, 발생 가능한 오류를 근본적으로 해결하고, 필요한 경우 기존 기능을 해치지 않는 범위에서 더 안정적이고 좋은 코드로 개선하여 실제 시제품 테스트에 최대한 안전한 상태로 만드는 것이다.

🚨 가장 중요한 작업 원칙



1. 기존 기능은 반드시 유지한다.



현재 정상적으로 작동하는 기능은 함부로 변경하거나 삭제하지 않는다.



다만 다음 조건을 만족한다면 코드를 개선하는 것은 허용한다.



«사용자가 경험하는 기능과 결과는 그대로 유지하면서 코드 자체를 더 안정적이고 효율적이며 유지보수하기 좋은 구조로 개선하는 것»

기능은 유지하고 코드는 더 좋아져도 된다.

기존 채팅 기능과 사용자 경험을 유지하는 범위에서 더 좋은 구조로 리팩터링해도 된다.



예:



- WebSocket lifecycle 개선

- 연결 상태 관리 개선

- 재연결 로직 개선

- 중복 연결 방지

- 중복 이벤트 리스너 방지

- 메시지 중복 방지

- 메시지 순서 보장

- 비동기 race condition 방지

- cleanup 처리 개선

- 메모리 누수 방지

- 실패 상태 처리 개선

- 메시지 전송 상태 관리 개선



이 경우 단순히 기존 코드에 임시방편을 추가하는 것보다 근본적으로 안정적인 구조를 선택한다.



단, 리팩터링 후 반드시 기존 채팅 기능 전체를 다시 테스트한다.

14. 실제 사용자 시나리오 테스트



코드를 읽는 것만으로 테스트를 끝내지 않는다.



실제 사용자가 이용하는 것처럼 테스트한다.



예:



회원가입

→ 로그인

→ 메인

→ 프로필

→ 상대방 확인

→ 매칭

→ 채팅방

→ 메시지 전송

→ 상대방 메시지 수신

→ 다른 페이지 이동

→ 다시 채팅

→ 새로고침

→ 로그아웃

→ 재로그인



이 전체 흐름을 테스트한다.

- 앞으로가기

- 빈 값

- 잘못된 값

- 긴 값

- 특수문자

- 네트워크 끊김

- 느린 네트워크

- API 실패

- 서버 응답 지연

- 존재하지 않는 URL

- 존재하지 않는 데이터

- 삭제된 데이터 접근



이런 상황에서도 서비스가 최대한 깨지지 않도록 한다.

현재 디자인을 유지하면서 깨지는 부분만 수정한다.

26. 중요한 판단 기준



이번 작업은 단순한 "코드 정리"가 아니다.



목표는 다음과 같다.



«현재 만들어진 하트시그널 웹 서비스를 실제 사용자가 테스트해도 최대한 안정적으로 사용할 수 있는 상태로 만드는 것»



따라서



"코드를 얼마나 많이 바꿨는가"가 아니라 "서비스가 얼마나 안정적으로 동작하는가"를 기준으로 판단한다.



필요하다면 기존 코드보다 훨씬 좋은 구조로 개선해도 된다.



하지만 반드시 기존 기능과 사용자 경험을 유지해야 한다.
